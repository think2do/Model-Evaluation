STEP01
PROMPT REVIEW

准备 01：把规则说清楚

检查用于生成评测题的提示词，删除冲突、隐藏要求和不稳定判断， 得到一份可重复使用的评测生成模板。

这一阶段只需记住 在写代码前，先把“什么叫做对”定义清楚。

产出：一份边界清楚、能够被下一步直接使用的提示词模板。

原始目标
“生成一道有明确区分度的模型评测题，以及与题目严格对应、 可以稳定执行的二元评分标准。”
  • 对象跨领域模型能力评测
  • 交付1 道题 + 12–18 个二元评分项
  • 判定每项只允许 0 或 1 分
  • 约束不依赖隐藏信息与整体印象
发现的核心矛盾
规则 A必须有 12–18 项
VS
规则 B不得重复或隐藏要求

对简单主题而言，可验证的独立要求可能不足 12 个。若强制凑数， 模型就可能拆得过细，甚至偷偷加入题目没有要求的偏好。

REVIEW FINDINGS

审查不是挑语病，而是寻找会让系统失稳的规则

01

评分项数量硬约束

固定 12–18 项会诱发“为了数量而设计”，与原子化、无隐藏要求产生冲突。

优先修正
02

重复扣分边界含糊

“同一缺陷不得重复扣分”要求裁判追溯根因，不同 AI 可能得到不同解释。

稳定性风险
03

设计方式强制组合

要求每道题至少使用两种设计手法，可能迫使窄任务添加不必要的取舍。

形式主义
04

工具输出不可复现

即使允许联网或运行代码，裁判环境也未必能重现当时版本与结果。

环境漂移
05

“原样包含”的冲突

规则要求固定文本原样输出，同时又要求替换评分项数量与满分。

指令冲突
06

输入缺失没有出口

主题为空或过宽时，模型缺少明确的停止条件，容易擅自补全核心任务。

失败路径
关键改造
“每个关键缺陷只能影响最相关的一个评分项，不得重复扣分。”

问题：裁判必须判断多个失败是否来自“同一个根因”，这不是稳定的静态文本判断。

“不同评分项只要检查的是不同原子结果，就分别根据各自证据判定。”

改造：不追溯根因，只检查可观察结果；评分项设计阶段负责避免两个项目检查同一事实。

ARTIFACT 01查看改写后的元提示词结构 展开

完整改写版把默认评分环境明确为“只看原始问题、评分标准和待评回答的静态文本判定”， 并形成以下八个部分。

  1. 输入配置增加“评分执行环境”，信息不足时只请求最少补充。
  2. 内部设计流程先建立题目要求与评分项的一一映射，并用边界样例测试。
  3. 题目生成要求写清工具边界、数据快照、运行环境和静态证据。
  4. 二元评分标准按难度设置数量范围，不为凑数添加隐藏要求。
  5. 评分项固定结构加入判定依据、接受的等价形式与归属边界。
  6. 红线规则最多两条；触发后仍给出全部原始项得分。
  7. 计分与裁判规则15 条固定规则统一证据、冲突与得分处理。
  8. 静默自检与输出格式输出前检查映射、数量、容差和满分一致性。
关键定义

“稳定执行”是指：不同裁判仅依据原始问题、评分标准和待评回答， 应能按照相同证据与判定步骤得到一致结果。

ARTIFACT 02查看题目与评分标准的关键原文 展开
题目中的边界 “不得补充留香时长、功效、成分、安全性、销量、折扣或用户反馈等未提供信息。”
评分的证据原则 “只有回答中存在满足该项‘1分条件’的明确证据时才能记1分。”
冲突处理 “同一检查对象出现互相冲突的内容且没有明确最终修正版本时，相关评分项记0分。”
等价形式 “15 ml”“15ML”可等价于“15mL”；“39 元”可等价于“39元”。

本题没有设置红线规则。原因是普通漏项、表达问题或单个事实错误， 都可以由对应的二元评分项处理，不需要把总分直接归零。

课堂观察

这里并没有真正“客观测量审美”。它测量的是一组被预先定义、 与平台文案风格相关的可观察行为。可复现性提高了，但测量范围也被明确收窄了。

STEP05
VIBE CODING

把手工裁判流程做成网页

Vibe Coding 不是“一句话生成整个产品”。这次过程被明确拆成两段： 前期先澄清范围并写成文档，后期按 M1–M9 逐个实现、测试和微调。

PHASE A / BEFORE CODE

先把需求说清楚

  • 只做裁判器，不做出题器
  • 问题、标准、回答由用户手动粘贴
  • 支持多个“模型名称 + 回答”
  • 纯前端、本地使用、无数据库
  • 结构失败时保留原始返回，不自动修复
PHASE B / BUILD & TUNE

再按小任务增量实现

  • 每次只交付一个可验收模块
  • 先静态骨架，再输入、请求、解析、展示
  • 根据真实使用反馈调整布局与标签页
  • 最后补本地验证和开源安全检查
贯穿每个环节的四个问题

不要只问“AI 写完了吗？”

01产出物是什么？
02AI 做什么？
03你做什么？
04什么算完成？
WEB CODING PLAYBOOK

九个环节：从一句想法，到一个你敢交付的版本

01需求澄清

先确定“做什么”，更要确定“不做什么”

AI 把口语想法整理成结构化需求；你检查它有没有加戏，并确认核心用户与核心场景。

本项目证据 《需求说明》 只做裁判器；删除出题器、后端、数据库等扩展
02技术方案

选择你能理解、能维护的最小方案

AI 解释可行方案与取舍；你判断复杂度是否匹配项目体量，而不是把决定完全交给 AI。

本项目证据 《技术选型与架构说明》 原生 HTML / CSS / JS；纯前端；无构建、无数据库
03任务拆解

把大需求拆成一次对话能验收的小任务

AI 标出依赖和顺序；你检查粒度，确保每项都有明确的输入、输出和验收方式。

本项目证据 《任务清单》M1–M9 每项可在一次对话 / 一个 commit 内完成
04环境与骨架

先让最小骨架在自己的机器上跑起来

AI 搭项目结构；你亲自打开、刷新、查看错误，并理解每个文件承担什么职责。

本项目证据 M1 基础页面 index.html + styles.css + app.js，可直接本地打开
05分模块开发

AI 每次只做一个任务，你每次立刻验证

不要让功能一次性堆满。每轮都要求说明改了什么、怎样验收，再决定是否进入下一项。

本项目证据 M2 → M8 逐项推进 输入、回答、请求、解析、展示、排序分别交付
06自测走查

正常路径能用，只代表测试刚刚开始

AI 列边界与潜在 bug；你亲自试空输入、非法 JSON、异常分数、网络失败等异常路径。

本项目证据 M5 / M6 验证 真实 API 通过；非 JSON、非法得分、缺失字段会被拒绝
07集成联调

模块单独能跑，不代表用户流程能跑通

把输入、请求、解析、结果和排序串起来；你从头走一遍真实核心路径，观察模块之间的接口。

本项目证据 完整评测路径 粘贴材料 → 多回答 → 发起裁判 → 结果标签 → 排名
08测试验收

回到最初需求，一条条核对状态

不要凭“看起来差不多”结束。每项都应是完成、部分完成或明确不做，并记录遗留问题。

本项目证据 布局与结果微调 样式简化、左右布局、回答标签、结果标签均来自验收反馈

代码阅读方法

面对 1200 多行的 `app.js`，不要按文件长度产生恐惧。沿着一次用户操作追踪即可： 填写 → 校验 → 构造任务 → 发请求 → 解析 → 排名 → 渲染。 每个函数都是前面任务清单中某个小任务的代码化结果。

当前可见 Git 记录 M3 → M4 → M5 → M6 → M7 → M7.1 → M8 → M9

这组提交证明后半段确实按模块演进；当前可见历史从 M3 开始， 因此不能把 M1、M2 说成可独立追溯的提交。

OPEN SOURCE CHECK

功能完成，不等于可以直接开源

M9 检查确认当前 `config.js` 已被 Git 忽略、待提交文件未发现本地 Key； 但历史扫描发现旧提交中的 `app.js` 曾包含真实 Key。 因此发布前必须先轮换旧 Key，并清理 Git 历史或从脱敏文件建立全新仓库。
