# 项目上下文

本文档是后续 AI 和开发者理解项目的首要入口。内容以当前代码为第一依据，以现有设计文档和 Git 历史为补充；无法从仓库确认的内容统一标记为“待确认”。

## 1. 项目目标

为个人本地使用提供一个简单的模型回答裁判器：

- 用户手动输入问题。
- 用户手动输入与问题对应的评分标准。
- 用户手动粘贴一个或多个候选模型回答，并填写模型名称。
- 页面调用 DeepSeek API 对每个回答进行独立评测。
- 页面以固定外壳、动态评分项的形式展示结果，并对有效结果排序。

核心问题不是“自动出题”，而是让不同数量、不同内容的二元评分项能够被稳定解析和展示。

## 2. 明确范围

### 当前包含

- 问题与评分标准输入。
- 多个候选回答的添加、删除和标签切换。
- 一候选回答一请求，并发调用 DeepSeek API。
- 对裁判 JSON 的严格校验。
- 逐项证据、理由、红线、总分、得分率和校验信息展示。
- 多模型结果标签切换与排名汇总。
- 超时、网络、HTTP、API、响应格式和解析错误展示。
- 桌面双栏与窄屏单栏布局。

### 当前明确不做

- 自动生成问题或评分标准。
- 自动调用其他模型生成候选回答。
- 登录、多人协作、后端服务、数据库或云端历史。
- 题库、批量导入、批量任务、定时任务。
- 固定一套通用评测维度。
- 自动修复裁判返回的非法 JSON。

导出报告、历史记录和批量能力是否纳入后续版本：**待确认**。

## 3. 已核实技术栈

| 层级 | 当前实现 |
| --- | --- |
| 页面 | HTML5 |
| 样式 | 原生 CSS，含响应式布局 |
| 逻辑 | 原生 JavaScript、DOM API |
| 脚本加载 | 经典脚本；`config.js` 后加载，`app.js` 使用 `defer` |
| 网络 | 浏览器 `fetch` + `AbortController` |
| 模型服务 | DeepSeek Chat Completions API |
| 当前模型标识 | `deepseek-v4-flash`，硬编码于 `app.js` |
| 数据存储 | 无；仅页面内存 |
| 构建与依赖 | 无 npm、无框架、无打包器 |
| 测试 | 仓库内未发现自动化测试套件 |

早期《技术选型与架构说明》提到 ES Modules，但当前代码不是 ES Module 结构。这是文档与实现的已确认差异。

## 4. 运行时模块

当前主应用逻辑集中在 `app.js`，按职责可理解为以下模块：

| 模块 | 主要职责 | 关键入口 |
| --- | --- | --- |
| 配置 | 读取本地 Key、API 地址和超时 | `LOCAL_CONFIG`、`DEEPSEEK_CONFIG` |
| 输入状态 | 管理问题、标准和候选回答 | `evaluationInput` |
| 候选回答 UI | 创建、删除、切换回答标签 | `addCandidate`、`removeCandidate`、`setActiveCandidate` |
| 请求构造 | 生成裁判提示词和请求体 | `buildJudgeRequest`、`buildJudgeJobs` |
| API 客户端 | 发起请求并分类错误 | `requestDeepSeek` |
| 严格解析 | 验证裁判结果的结构和计分一致性 | `parseJudgeResponse` |
| 排名 | 对有效结果稳定排序 | `rankJudgeResults` |
| 结果视图 | 渲染排名、结果标签和详情卡片 | `renderJudgeResults`、`setActiveResult` |

`process-recap/` 是另一套独立静态页面，用于课堂展示项目形成过程。它不依赖、也不参与主裁判器运行。

## 5. 关键设计约定

### 输入与候选回答

- 候选回答使用运行时生成的唯一 `candidateId` 关联请求和结果。
- 页面至少保留一个候选回答。
- 提交评测时冻结输入、添加、删除和提交操作。
- 多个候选回答通过 `Promise.all` 并发评测。

### 裁判请求

- 问题、评分标准、模型名、候选 ID 和回答被包装为 JSON 文本发送。
- 请求要求服务返回 JSON 对象，且禁止使用 Markdown 代码围栏。
- 每个候选回答单独请求，单个失败不应阻止其他结果展示。
- 当前超时为 300000 毫秒。

### 结果解析

- 采用“严格失败”策略：返回结构不合规时标为 `parse-error`，不猜测、不补字段、不自动纠正分数。
- 评分项 ID 必须匹配 `C` 加数字，并且不能重复。
- 单项分数只允许 `0` 或 `1`。
- `maxScore` 必须等于评分项数量。
- 单项得分之和必须等于 `rawScore`。
- 未触发红线时，`finalScore` 必须等于 `rawScore`。
- `scoreRate` 必须等于 `finalScore / maxScore` 四舍五入后的整数百分比。
- 解析失败时保留原始返回文本，供人工排查。

### 排名与展示

- 只有解析成功的结果参与排名。
- 按最终分从高到低排列；同分使用竞赛排名，例如 `1、2、2、4`。
- 同分时保留候选回答原始顺序。
- 失败结果排列在有效结果之后，并明确显示错误类型。
- 模型名称只作为标签，不参与评分。

### 安全与配置

- `config.example.js` 可以提交，真实 `config.js` 必须保持在 `.gitignore` 中。
- 不得在源码、文档、截图、日志或提交信息中写入真实 Key。
- 前端配置无法对浏览器隐藏 Key，因此项目只适合受控的本地个人场景。
- Git 历史中曾出现真实 Key，发布前必须完成 Key 轮换和历史清理。

## 6. 开发约定

- 保持零构建、零运行时依赖，除非需求明确改变。
- 修改行为时优先维持已有状态值：`pending`、`loading`、`success`、`error`、`parse-error`。
- 渲染用户文本和模型文本时使用 `textContent`，避免把内容直接作为 HTML 注入。
- 新增评测字段时，同时更新请求提示词、解析器、结果渲染和文档。
- 解析器应继续拒绝含糊或自相矛盾的数据，不进行善意推断。
- 错误必须在对应模型结果中可见，不能静默吞掉。
- 保持桌面与移动端都能完成核心操作。
- 每个功能变更尽量保持为可独立验收的小任务。
- 提交前检查 `config.js` 仍被忽略，并扫描新增内容是否包含凭据。

代码格式化、命名规范、浏览器支持范围和正式版本规则：**待确认**。仓库内未发现 ESLint、Prettier、EditorConfig 或版本配置。
