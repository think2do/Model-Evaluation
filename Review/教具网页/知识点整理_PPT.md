### 知识点整理 · 从模糊想法到可维护项目

- 第一部分：构建项目 —— 执行清单十个环节（方法 + 案例）
- 第二部分：维护项目 —— 项目文档与交接
- 第三部分：项目复盘与课堂总结

> **🎤 演讲者注释**：开场自我介绍与课堂定位。今天用一个真实项目——"多模型答案对比评测器"（裁判器）——完整走一遍从模糊想法到本地可运行网页的过程，并把整套方法拆成可复用的执行清单。强调三点：这套方法不是 AI 的清单，是你的清单；每一轮都有人工验证；最终目标是你理解、敢用、能继续维护的项目。

# 环节 0：项目启动

- **核心**：跟 AI 聊天把模糊想法收敛成可执行方向，**而不是直接让 AI 写代码**
- **产出物**：一句话定位 + 初步想法（功能方向、目标人群、大致形态）
- **你**：用自己的话讲出模糊想法（不用讲究逻辑）；**AI**：通过提问帮你理清"到底想解决什么问题"
- **结束标准**：能用一两句话说出"想做什么、大概解决什么问题"，从"灵感"收敛到"可以进需求澄清"
- **案例证据**：**代码是工作流被理解之后的结果，不是项目的第一步**
  - 想法来自已验证的手工流程（Step 01–04 手工跑通）→ 复制粘贴、逐份请求、结果复核等重复劳动成为产品化理由

**📋 可直接发给 AI 的 Prompt**

```text
我有一个模糊的想法,还没想清楚细节,请不要直接给方案或写代码。
先通过提问帮我理清楚:
1. 这个想法本质上是想解决什么问题
2. 大概是给谁用的
3. 现在最核心、最想先做出来的部分是什么
一步步引导我把这个想法聊清楚,聊完之后帮我总结成一句话定位。
```

> **🎤 演讲者注释**：讲解方法时带出 Prompt 要点——"不要给方案、先通过提问帮我理清楚"。建议现场把这段 Prompt 完整演示一遍（可直接复制），让学员直观看到"不给方案、只提问"的实际效果，最后落成一句话定位。本项目证据非常关键：最初不是"想写个网页"，而是先有了一套手工评测流程（Step 01–04），因为重复劳动太多，才产生"做成工具"的需求。一句话记住：**已验证的手工流程成为产品需求**。可以用这个例子反问听众："你手上有没有重复劳动，值得做成工具？"

# 环节 1：需求澄清与范围确定

- **产出物**：《需求说明》——要做什么、给谁用、核心场景、**明确不做什么**
- **你**：讲清想法 + 划清"必须有 / 暂时不要"的边界；**AI**：口语描述 → 结构化需求（功能点 + 边界），主动追问模糊点，**不自己脑补**
- **结束标准**：一句话说清"做完是什么样子"；AI 复述的需求和你脑子里想的一致，没有"AI 自己加戏"的功能
- **案例证据**：《需求说明》只做裁判器；PHASE A 需求清单：纯前端、本地使用、无数据库、结构失败保留原始返回不自动修复
- **决策日志 03（范围纠偏）**：删除"出题器"扩展——先确定做什么，更要确定不做什么
- **关键**：需求清单是**环节 8 验收的依据**（逐条核对 完成/部分完成/不做）

**📋 可直接发给 AI 的 Prompt**

```text
请帮我把这个想法整理成结构化的需求说明,包括:
1. 核心功能点(列清单)
2. 目标用户是谁
3. 最核心的使用场景是什么
4. 明确列出"这一版先不做"的部分

将生成的文档存到项目根目录下的 `docs/*****需求文档.md`。
如果我的描述里有模糊、矛盾或者信息不够的地方,请直接指出来并追问我,
不要自己脑补细节替我做决定。
```

> **🎤 演讲者注释**：重点讲"AI 加戏"这个概念——AI 整理需求后，你要逐条检查它有没有擅自加功能、替你拍板。本项目三次范围纠偏：只做裁判器、删出题器、删后端数据库。强调范围控制不是"少做"，而是"这一版做完、做扎实"。需求清单后面会反复出现：环节 8 用它验收，环节 1 的手工材料（13 项标准）则成为验收正确性的基准。

# 环节 1 案例：三个手工前置（写代码前的准备）

- **手工前置 1/3 · STEP 01 准备规则**：在写代码前定义"什么叫做对"——检查评测提示词，删除冲突、隐藏要求和不稳定判断，得到可重复使用的评测模板；"稳定执行"= 不同裁判凭相同证据得到一致结果
- **手工前置 2/3 · STEP 02 准备测试**：把抽象目标转成可观察要求——"有网感"不直接评价，而是要求"首句有场景钩子、固定对比句式、回复指定关键词、emoji ≤ 3"；产出题目 + **13 项二元评分标准**（C01–C13，核心是"有没有明确证据"）
- **手工前置 3/3 · STEP 03 准备回答**：题目 → 模型生成回答 → 得到可被重复裁判的静态材料；网页评测的是"用户粘贴进来的回答"，不是自动生成答案

> **🎤 演讲者注释**：这页是环节 1 的重要补充：需求澄清不止是写文档，还要制造出"可评测的材料"。关键转变是**抽象目标 → 可观察要求**（举"有网感"的例子）。13 项评分标准是全场最重要的基准物：环节 6 的稳定性测试、环节 8 的验收都以它为准。可以现场提问：还有什么抽象标准很难转成可观察要求？

# 环节 2：技术方案设计

- **产出物**：技术选型说明（语言/框架/库、为什么）+ 简要架构或数据流转 + 数据结构草图（如需）
- **AI**：给出可行方案并说明取舍（不是直接甩代码）；**你**：审核方案是否匹配你的能力（能维护）、匹配项目体量（别小项目上重架构）
- **看不懂方案怎么办（不要假装懂了往下走）**
  - "用大白话/打比方跟我解释一遍"
  - "假设我是完全不懂技术的人，怎么讲清楚这个方案在做什么"
  - "有没有更简单但够用的方案？性能差一点没关系"
- **判断标准**：AI 讲完后，你能用自己的话复述"这个方案大概怎么回事"，才往下走
- **案例证据**：《技术选型与架构说明》——原生 HTML / CSS / JS，纯前端，无构建、无数据库

**📋 可直接发给 AI 的 Prompt**

```text
基于以上确定的需求,请给我可行的技术方案。

对每个方案请说明:
1. 技术选型说明(用什么语言/框架/库,为什么)
2. 简要架构图或文字描述(模块划分、数据怎么流转)
3. 如果涉及数据存储:数据结构/表结构草图
4. 大致用什么技术/工具(不用列太细)
5. 优缺点和取舍是什么
6. 用大白话/打比方讲清楚这个方案是在做什么,不要堆专业术语

将生成的文档存到项目根目录下的 `docs/*****技术方案.md`。
最后请告诉我这个方案里有没有"我以后自己改代码时特别容易踩坑"的地方。
```

> **🎤 演讲者注释**：强调"看不懂就问到底"是这一环节最重要的动作——**"假装懂了"是后面失控的最大源头之一**。给出的追问话术直接来自课堂 Prompt。本项目为什么选纯静态三件套？因为匹配体量：本地单人使用的裁判器，不需要框架、构建和数据库。让听众体会"简单但够用"的取舍逻辑。

# 环节 3：任务拆解与排期

- **产出物**：任务清单（Task List）——每个任务可在**一次对话 / 一个 commit** 内完成，可独立验收
- **AI**：把大需求拆成小任务，标注任务间依赖（哪个必须先做）；**你**：检查拆分粒度——太大没法中途检查，太碎失去整体感
- **结束标准**：每个任务有清晰验收方式（"输入 A 输出 B""页面能看到 X"）；知道推进顺序，不是走一步看一步
- **案例证据**：任务清单 **M1–M9**；文档链：01 需求说明 → 02 技术与架构 → 03 任务清单（需求层层落实）
- **Git 边界（诚实原则）**：可见历史从 M3 开始，**不能说 M1、M2 是可独立追溯的提交**

**📋 可直接发给 AI 的 Prompt**

```text
请把我们确定的方案拆解成一个具体的任务清单。

要求:
1. 每个任务要足够小,能在一次对话/一次提交里做完
2. 标注任务之间的先后依赖关系(哪个必须先做完才能做下一个)
3. 每个任务都附上"怎么算这个任务做完了"的验收标准
   (要具体到我能亲自操作验证,比如"打开某页面应该看到什么"
   或"调用某个函数输入什么应该输出什么")

将生成的文档存到项目根目录下的 `docs/*****任务清单.md`。
请按顺序编号列出。
```

> **🎤 演讲者注释**：展示 M1–M9 是下一页的表格。本页强调两件事：一是**验收标准必须具体到能亲自操作验证**（打开某页看到什么 / 调用某函数输入什么输出什么）；二是**诚实对待 Git 历史**——当前仓库可见记录从 M3 开始，就不能把 M1、M2 说成独立提交。这既是方法也是态度。

# 环节 3 案例：M1–M9 增量交付清单

| 里程碑 | 内容 | 说明 |
| --- | --- | --- |
| M1 | 页面骨架 | 输入区 / 结果区 / 空状态 |
| M2 | 问题与标准 | 长文本录入与空值校验 |
| M3 | 多份回答 | 新增 / 删除 / 标签切换 |
| M4 | 裁判请求 | 单回答单请求 + JSON 契约 |

# 环节 4：环境搭建与脚手架

- **产出物**：可运行的项目骨架（能启动、能看到空白页面 / 接口返回 200）+ 目录结构说明
- **AI**：搭建项目结构、配置基础依赖；**你**：**亲自跑一遍启动命令**，确认在自己机器上真的能跑（不是只在 AI 的描述里能跑）
- **结束标准**：本地成功启动无报错；理解目录结构里"哪个文件夹放什么"的基本逻辑
- **案例证据**：M1 基础页面——`index.html` + `styles.css` + `app.js`，纯静态可直接打开，无需构建
- **骨架内容**：输入区 / 结果区 / 空状态（空状态是页面"名词"与区域的第一版雏形）

**📋 可直接发给 AI 的 Prompt**

```text
请帮我搭建这个项目的基础脚手架(目录结构 + 必要依赖),先不用写业务逻辑。

完成后请告诉我:
1. 目录结构里每个主要文件夹/文件是干嘛的(简单一句话说明)
2. 我需要在终端里依次敲哪些命令,才能把项目跑起来
3. 跑起来之后,我应该在浏览器/终端里看到什么,
   才能确认"搭建成功了"
```

> **🎤 演讲者注释**：强调"跑起来"这件事必须由你亲自完成——AI 说能跑不算数。本项目因为是纯静态三件套，打开方式最简单：直接双击 `index.html`，或起任意静态文件服务器。可以讲：骨架阶段的"空状态"很有价值，它提前定义了页面有哪些区域，后面每个模块都往这些区域里填内容。

# 环节 5：分模块开发实现

- **产出物**：按环节 3 任务清单**逐个交付**的功能代码（每次一个小任务，不一次甩一大坨）
- **AI**：每次只做一个约定好的小任务，做完主动说明"改了什么文件、实现了什么逻辑"
- **你**：**每个小任务做完后立刻验证**，不要攒到最后一起看（这是最容易失控的环节）
- **结束标准**：当前任务功能你亲自验证过（跑起来、点按钮、发请求）；没有"AI 说做完了，但我没看"的任务
- **案例证据**：M2 → M8 逐项推进——输入、回答、请求、解析、展示、排序分别交付；每轮要求说明改了什么、怎样验收，再决定下一项

**📋 可直接发给 AI 的 Prompt**

```text
现在请只完成任务清单里的【任务X:具体任务名】,不要顺带做其他任务。
每次执行一个任务并进行验证,待验证通过后提交一个commit后再开始下一个任务,
不要一次性做完所有任务再验证。

每一步做完之后请告诉我:
1. 改动了哪些文件(简单列出,不用贴全部代码)
2. 每处改动实现了什么逻辑(用大白话说)
3. 需要我验证的告诉我应该怎么操作才能验证这个任务确实做成了
   (具体到"打开哪个页面/敲哪条命令/点哪个按钮,应该看到什么结果")
```

> **🎤 演讲者注释**：这页是"节奏控制"的核心。课堂反复强调：**AI 天然倾向于一口气多做，你要主动喊停、分批验证**。给听众一个可执行的习惯：每个任务完成后让 AI 回答三个问题——①改了哪些文件 ②每处改动实现了什么逻辑（大白话）③我怎么操作才能验证成功。验证通过才 commit，再进下一个任务。

# 环节 5 案例：代码证据（app.js 关键函数）

```javascript
function buildJudgeRequest(input, candidate) {
  return {
    model: "deepseek-v4-flash",
    messages: [
      { role: "system", content: JUDGE_SYSTEM_PROMPT },
      { role: "user", content: buildJudgeUserPrompt(input, candidate) },
    ],
    response_format: { type: "json_object" },
    stream: false,
  };
}

function buildJudgeJobs(input) {
  return input.candidates.map((candidate) => ({
    candidateId: candidate.id,
    modelName: candidate.modelName,
    request: buildJudgeRequest(input, candidate),
  }));
}
```

- **要点**：`buildJudgeJobs` 为每份回答生成独立请求（单回答单请求 + JSON 契约）
- `response_format: json_object` 与 `stream: false` 是 M4"JSON 契约"的具体落地
- Git 记录证明模块演进：M3 → M4 → M5 → M6 → M7 → M7.1 → M8 → M9

> **🎤 演讲者注释**：用真实代码说明"任务清单 → 函数"的映射关系：M4 的任务是"裁判请求"，落到代码就是这两个函数。让听众看到：**每个函数都是前面任务清单里某个小任务的代码化结果**，所以阅读代码时不要恐惧文件长度（app.js 有 1200 多行），沿着任务线索读即可。

# 环节 6：自测与代码走查

- **产出物**：关键逻辑的测试结果（手动测试记录即可，不一定要自动化）+ 一份"已知问题 / 边界情况"清单
- **AI**：主动列出没覆盖到的边界情况、可能的 bug 点；**你**：挑几个边界场景（空输入、异常输入）亲自试，**不要只测正常路径**
- **结束标准**：正常场景 + 至少 1–2 个异常场景手动验证过；已知的坑你清楚，而不是"看起来能用就行"
- **案例证据**：M5 / M6 验证——真实 API 通过；非 JSON、非法得分、缺失字段会被拒绝
- **决策日志 04（失败策略）**：宁可暴露失败，也不伪造正常——结构失败时保留原始返回，要求人工复核，**不自动修复**

**📋 可直接发给 AI 的 Prompt**

```text
请针对刚才实现的【具体功能/模块名】,帮我做一次自查:

1. 列出这段代码可能没覆盖到的边界情况和潜在 bug 点
   (比如空输入、异常输入、极端值、网络失败等)
2. 针对每一条,给我具体的手动测试步骤,让我可以逐一验证
   (不需要写自动化测试代码,手动操作步骤就行)
3. 哪些问题你觉得现在必须修,哪些可以先记下来暂不处理
```

> **🎤 演讲者注释**：强调"正常路径能用，只代表测试刚刚开始"。AI 列的边界清单要落到你手上变成手动测试步骤：空输入、非法 JSON、异常分数、网络失败（超时/错误状态）。决策日志 04 是很好的产品观讨论点：遇到坏结果，是"假装成功"还是"诚实失败"？本项目选择暴露失败并引导人工复核。

# 环节 6 案例：四轮重复裁判验证（STEP 04 稳定性测试）

| 轮次 | 得分 | 结果 | 标题汉字数 |
| --- | --- | --- | --- |
| ROUND 01 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |
| ROUND 02 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |
| ROUND 03 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 15 |
| ROUND 04 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |

- **稳定性两层结论**：核心结论 4/4 一致（总分 12/13、92%、唯一失分项 C06）；**局部漂移 14 ↔ 15**（第三轮标题汉字计数不同，但落在 14–20 通过区间）
- **C06 分析**：回答"不是为了多复杂的步骤……"语义形成对比，但标准要求"不是/是"之间必须出现"……"或"..."——**逻辑满足 ≠ 字面格式满足**
- **稳定性三层**：总分 → 分项结论 → 证据与理由（只看总分会误判"很稳定"）
- **意义**：四轮稳定性测试证明**需求真实存在**；已验证的手工裁判流程成为 Step 05 的产品原型

> **🎤 演讲者注释**：这页是全场最有教学密度的一页。第一层：四轮总分一致，看似"裁判很稳定"；第二层：继续比分项，才发现标题汉字数有 14↔15 的漂移——所以稳定性必须分三层看。C06 的教训：评分标准是字面条件，逻辑上说得通但格式不满足就是 0 分，四轮裁判都严格执行。这个案例同时回答了一个大问题：为什么值得做裁判器？因为需求已被验证真实存在。

# 环节 7：集成联调

- **产出物**：各模块拼在一起后**端到端跑通**的完整流程
- **AI**：把之前分开开发的模块接起来，解决接口 / 数据格式不匹配；**你**：走一遍完整用户路径，而不是只看单个模块
- **结束标准**：环节 1 定义的核心使用路径能从头到尾走通一次；没有"模块 A 单独能跑、模块 B 单独能跑、连起来就报错"
- **案例证据**：完整评测路径：粘贴材料 → 多回答 → 发起裁判 → 结果标签 → 排名
- **项目数据流**：`INPUT → BUILD → REQUEST → PARSE → OUTPUT`
- **代码阅读方法**：1200 多行 `app.js` 不可怕——沿一次操作追踪：填写 → 校验 → 构造任务 → 发请求 → 解析 → 排名 → 渲染

**📋 可直接发给 AI 的 Prompt**

```text
现在请帮我把已经完成的各个模块整合起来,
确保【核心使用路径,比如"从首页到提交成功"】能完整走通。

整合完成后请给我一份端到端的操作步骤清单,
让我能从头到尾亲自走一遍这个流程来验证。

如果整合过程中发现模块之间接口/数据格式对不上,
请说明是怎么解决的。
```

> **🎤 演讲者注释**：讲联调时顺便教"怎么读长代码"：不要按文件长度产生恐惧，沿着一次用户操作追踪即可，每个函数都是某个小任务的代码化结果。联调用的输入数据不是随便编的——正是环节 1 手工准备的材料（Step 02 题目与 13 项标准、Step 03 回答）。这就是"需求层层落实"的闭环：环节 1 造材料 → 环节 5 写功能 → 环节 7 用材料联调。

- **你**：拿最初的需求清单一条条核对是否做到；**AI**：协助定位"做出来但不符合预期"的问题根因
- **结束标准**：每条状态是"完成 / 部分完成 / 不做"，而不是"不确定"；**你敢把这个版本给别人用**

对于"部分完成"或"未做"的条目,请说明原因,

> **🎤 演讲者注释**：验收态度一句话：**不要凭"看起来差不多"结束**。四条反馈说明"做完了"不等于"做好了"——界面是在真实使用反馈中被改写的。强调验收正确性来自环节 1 定义的材料：13 项评分标准是核对"裁判结果是否正确"的对照清单，环节 6 的四轮重复裁判结论是基准值。下一页给出最终验收结果。

# 环节 8 案例：最终验收结果（对照需求清单）

- **✅ 最终做到了**：输入原始问题与评分标准；手动录入并切换多份回答；独立调用裁判并处理请求状态；严格解析 JSON 展示逐项证据；前端排序、并列名次与失败隔离
- **⛔ 明确没有做**：出题器 / 自动生成回答；登录、后端、数据库和历史记录；复杂自动修复或多轮纠错；题库、批量导入导出与报表；在安全处理前直接公开 Git 历史
- **验收正确性**：13 项评分标准（C01–C13）= 判断"裁判结果是否正确"的对照清单；四轮重复裁判结论（环节 6）= 验收的基准值

> **🎤 演讲者注释**：强调"明确不做"也是验收结果的一部分——它证明环节 1 的范围控制贯彻到了最后，每条都能对应回 PHASE A 需求清单和决策日志。让听众看到：验收不是收尾动作，而是从环节 1 就设计好的闭环。可以用这页反推：如果你的验收清单是从需求清单来的，就不会出现"做完了但不知道算不算完成"。

# 环节 9：开发完成确认（交付前收尾）

- **产出物**：最终代码 + 一份简要说明（怎么运行、有什么已知限制）
- **AI**：整理"这个版本做了什么、没做了什么、怎么跑"的总结；**你**：通读一遍，确认总结与你的理解一致
- **结束标准**：即使过一个月回来看说明，也知道当时做到哪一步；状态是"我清楚现在的样子"，而不是"AI 说做完了我就信了"
- **案例证据**：M9 README + 开源检查——使用说明、边界、验证记录、Key 与 Git 历史风险
- **⚠️ 安全教训（功能完成 ≠ 可以直接开源）**
  - 当前 `config.js` 已被 Git 忽略、待提交文件未发现本地 Key
  - **但历史扫描发现旧提交中的 `app.js` 曾包含真实 Key**
  - 发布前必须先**轮换旧 Key**，并**清理 Git 历史或从脱敏文件建立全新仓库**

**📋 可直接发给 AI 的 Prompt**

```text
请帮我整理一份这个版本的总结文档,包括:

1. 这个版本做了哪些功能(简明列出)
2. 有哪些已知限制或还没做完的部分
3. 怎么运行这个项目(命令 + 步骤)
4. 如果我以后要接着改这个项目,有什么需要特别注意的地方
   (比如容易踩坑的模块、临时方案以后要替换的地方等)
```

> **🎤 演讲者注释**：用真实的安全教训收尾第一部分的案例：功能全部完成，但开源检查发现历史提交里曾提交过真实 API Key——即使现在的代码已脱敏，历史仍然泄露。所以"做完"只是第一步，"安全交付"还有一道检查。方法印证：最终代码之外，还要留下可恢复的项目状态——AI 整理怎么运行、做了什么、没做什么，你确认说明与真实状态一致。

# 贯穿全流程的一条原则

> **AI 交付节奏 vs 你的验证节奏要匹配**

- AI 天然倾向于一口气多做，你需要主动"喊停"、分批验证
- **之前项目不理想，大概率就出在环节 5–6**：AI 一次产出太多，你没能逐块验证，问题堆积到后面才爆发
- 网页 Step 05 的推进方式（"开始 M2 / M3 / … / M9"）本质是在控制风险：**上一块没有看懂、没有验证，就不进入下一块**
- **人机分工**：人持续负责方向、取舍和验收；AI 负责结构化、实现、解释和暴露风险——只有双方职责清楚，"会聊天"才会变成"会 Coding"
- 每个环节都回答四个问题：**产出物是什么 / AI 做什么 / 你做什么 / 什么算完成**

> **🎤 演讲者注释**：这是第一部分最重要的一页，适合停下来让听众思考。可以提问："你上一次项目失控，卡在哪一步？"答案大概率落在环节 5–6。核心观点：Vibe Coding 的价值不是"AI 写了多少代码"，而是人把住了方向、范围、节奏和验收。四问模板（产出物/AI/你/完成标准）可以套用到任何环节，也是第二部分文档维护的基础思维。

# 第二部分 2.1：初始化项目文档

- **场景**：项目开发过程中，让 AI 自动整理项目文档
- **产出**：在 `docs/` 目录生成六份文档（没有则创建）
  - `README.md`（项目介绍、安装、启动方式）
  - `PROJECT_CONTEXT.md`（背景、技术栈、模块说明、开发约定——**最重要**）
  - `ARCHITECTURE.md`（架构、目录结构、数据流）
  - `ROADMAP.md`（已完成、开发中、未来规划）
  - `CHANGELOG.md`（当前版本及后续更新记录）
  - `TODO.md`（待开发功能、Bug、技术债）
- **要求**：根据代码自动分析不凭空猜测；无法确定标「待确认」；简洁清晰；最后总结哪些需人工补充

**📋 可直接发给 AI 的 Prompt**

```text
请先完整阅读当前项目，然后自动整理项目文档。

根据代码、目录结构、配置文件和已有文档，在 docs/ 目录生成（没有则创建）：

- README.md              # 项目介绍、安装、启动方式
- PROJECT_CONTEXT.md     # 项目背景、技术栈、模块说明、开发约定（最重要）
- ARCHITECTURE.md        # 项目架构、目录结构、数据流
- ROADMAP.md             # 已完成、开发中、未来规划
- CHANGELOG.md           # 当前版本及后续更新记录
- TODO.md                # 待开发功能、Bug、技术债

要求：

1. 尽量根据代码自动分析，不要凭空猜测。
2. 无法确定的信息统一标记为「待确认」。
3. 文档使用 Markdown。
4. 内容简洁、清晰、方便后续 AI 和开发者阅读。
5. 最后总结哪些内容需要我人工补充。
```

> **🎤 演讲者注释**：第二部分解决"项目做完之后怎么长期维护"。核心痛点是：AI 对话不保留记忆，文档是唯一跨对话的载体。2.1 让 AI 在建项目时就把文档建起来，六份文档各司其职；其中 PROJECT_CONTEXT.md 最重要——它承载技术栈、模块说明和开发约定，是后续 AI 继续开发的"上下文"。

# 第二部分 2.2：新对话接管项目

- **场景**：新对话 / 新同事接管一个开发中的项目
- **流程**：先读 docs 全部文档 → 总结理解 → 说明已完成 / 待开发 → **指出文档与代码不一致处** → 等下一步需求
- **硬性约定**：不要立即修改代码，等待我的下一步需求

**📋 可直接发给 AI 的 Prompt**

```text
这是一个已经开发中的项目。

请先阅读 docs 目录下的所有项目文档，包括：

- README.md
- PROJECT_CONTEXT.md
- ARCHITECTURE.md
- ROADMAP.md
- CHANGELOG.md
- TODO.md

阅读完成后：

1. 总结你对当前项目的理解。
2. 说明当前项目已经完成了什么。
3. 说明还有哪些待开发内容。
4. 如果发现文档与代码不一致，请指出并给出建议。
5. 后续所有开发都以最新代码和这些文档为准。

不要立即修改代码，等待我的下一步需求。
```

> **🎤 演讲者注释**：2.2 的关键设计是"先复述、再动手"——新对话必须先总结理解、指出不一致，等指令后才改代码。这能防止新对话瞎改：它没有权限自作主张，同时文档和代码不一致的问题也会被主动暴露出来。可以强调：接管项目的仪式感越强，后期返工越少。

# 第二部分 2.3：开发完更新

- **场景**：每完成一次开发后，让文档跟着代码走
- **动作**：根据本次代码变更自动更新 `CHANGELOG.md`、`PROJECT_CONTEXT.md` 和 `TODO.md`，保持文档与代码同步
- **边界**：除非必要，不修改其他文档

**📋 可直接发给 AI 的 Prompt**

```text
本次开发已完成，请根据本次代码变更自动更新 CHANGELOG.md、PROJECT_CONTEXT.md 和 TODO.md，保持文档与代码同步。除非必要，不修改其他文档。
```

> **🎤 演讲者注释**：2.3 是第二部分最容易被忽略的一步——"开发完顺手更新"。很多项目的问题不是没写文档，而是文档停在第一版、代码已经跑远了。只更新三份最相关的文档（变更记录、上下文、待办），成本低、效果好，避免"代码和文档两张皮"。可以结合环节 9 讲：环节 9 是交付时的一次性说明，2.3 是每次开发后的常态化同步。

# 第二部分：老项目构建（2.4）

- **场景**：接手一个已有项目（可能没文档、历史混乱），为它补充项目文档
- **AI 先阅读**：目录结构 / 核心代码 / 配置文件 / 依赖文件 / 已有 README / Git 信息
- **生成同样六份文档**（README / PROJECT_CONTEXT / ARCHITECTURE / ROADMAP / CHANGELOG / TODO）
- **两条硬要求**：
  1. **不要凭空编造**，只根据代码和项目情况分析；不确定的信息标记「待确认」
  2. 完成后告诉你：对项目的整体理解、哪些内容是推测、哪些地方需要人工补充

**📋 可直接发给 AI 的 Prompt**

```text
请分析当前项目，并为这个已有项目补充项目文档。

请阅读：

- 项目目录结构
- 核心代码
- 配置文件
- 依赖文件
- 已有 README（如果存在）
- Git 信息（如果可以获取）

根据项目实际情况，在 docs/ 目录生成以下文件：

- README.md
  项目介绍、功能说明、安装和启动方式

- PROJECT_CONTEXT.md
  项目背景、技术栈、核心模块、开发规范，作为 AI 后续开发参考

- ARCHITECTURE.md
  项目架构、模块关系、主要流程

- ROADMAP.md
  当前完成情况、未来可能规划

- CHANGELOG.md
  根据代码和 Git 信息整理已有版本变化

- TODO.md
  当前待优化、待开发、技术债

要求：

1. 不要凭空编造，只根据代码和项目情况分析。
2. 不确定的信息标记为「待确认」。
3. 文档保持简洁、清晰，方便后续 AI Coding 使用。
4. 完成后告诉我：
   - 你对项目的整体理解
   - 哪些内容是推测
   - 哪些地方需要人工补充
```

> **🎤 演讲者注释**：对比 2.1 与 2.4 的区别：2.1 是在项目开发过程中由 AI 自动初始化文档；2.4 是面对一个"已经存在、可能很乱"的老项目补文档，风险更高——所以更强调"只根据代码分析、不编造"。CHANGELOG 在 2.4 里可以依据 Git 信息整理版本变化。最后一步很重要：AI 必须坦白哪些是推测，把"人工确认清单"交给你，而不是假装全部确定。

# 第三部分：可重复的 Coding 方法（五层倒序）

| 层级 | 关注点 | 一句话 |
| --- | --- | --- |
| 05 交付说明与安全收尾 | 知道现在做到哪里 | 留一份"一个月后还能看懂"的说明 |
| 04 联调、测试与需求验收 | 亲自跑通完整路径 | 对照需求逐条打勾，敢拿给别人用 |
| 03 分模块实现与即时验证 | 一次只交付一个任务 | 每块看懂、验证，再进下一块 |
| 02 技术方案与任务清单 | 知道为什么这样做 | 能解释取舍，任务有验收方式 |
| 01 需求澄清与范围边界 | 先决定做什么、不做什么 | 一句话定位 + 边界清单 |

> **🎤 演讲者注释**：倒序展示是有意为之——从"交付时知道做到哪"往下追问，每一层都依赖下一层：要能收尾，必须验收过；要验收，必须联调测试过；要联调，必须逐块实现并验证过；要实现，必须先有方案和任务清单；要有方案，必须先想清楚需求和边界。这就是"由表及里"的拆解逻辑，也让听众理解为什么环节 0–3 的"想清楚"如此重要。

# 第三部分：核心方法论 + 课堂主线

**核心方法论**
- AI 可以快速写代码，但**你要控制方向、范围、节奏和验收**
- 每一轮都留下明确产出，每一个小任务都立刻验证
- 最终得到的才不是"一堆 AI 生成代码"，而是一个**你理解、敢用、能继续维护的项目**

**课堂主线**
- 覆盖从模糊想法到本地可运行网页的完整 Coding 路径
- **四轮稳定性测试证明需求真实存在；九环协作清单和 M1–M9 才是本课程的核心方法**
- 课堂主线公式：**定义质量 → 制造测试 → 生成回答 → 验证稳定 → 编码工具**

> **🎤 演讲者注释**：收束全场的高潮页。把"会聊天"升级成"会 Coding"的关键：人在回路（Human-in-the-loop）——AI 提供速度，人提供方向。课堂主线公式对应到手工前置：定义质量（STEP 01 规则）→ 制造测试（STEP 02 题目与 13 项标准）→ 生成回答（STEP 03）→ 验证稳定（STEP 04 四轮裁判）→ 编码工具（Step 05 网页）。下一个项目复用指令：以"需求澄清 → 技术方案 → 任务拆解 → 分模块实现 → 自测 → 联调 → 验收 → 交付"推进。

# 附：网页交互功能（script.js）

- **章节导航高亮**：滚动时按 `scrollY + 视口高度 × 32%` 判断当前章节，高亮侧边导航
- **阅读进度条**：侧边栏竖向进度条随滚动比例增长

> **🎤 演讲者注释**：简要说明"知识点整理"这份材料来自一个教学网页，网页上有四个自研交互：章节高亮、阅读进度、改造前后对比、复制按钮。如果时间紧可以一句话带过；如果时间充裕，可以现场演示复制按钮和章节导航，让听众看到"教具"本身也是个小项目——它同样遵循了环节 0–9 的方法论。
