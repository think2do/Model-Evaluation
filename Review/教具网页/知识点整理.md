# Web Coding × AI 协作课堂复盘｜知识点整理

# 第一部分：构建项目 —— 执行清单十个环节（方法 + 案例补充）

## 十个环节概览

- **环节 0：项目启动**——把模糊想法先收敛成可执行方向。
- **环节 1：需求澄清**——把“要做什么”说清楚，并明确“不做什么”。
- **环节 2：技术方案设计**——选一个足够简单、能落地的实现方案。
- **环节 3：任务拆解与排期**——把大目标拆成可验证的小任务。
- **环节 4：环境搭建**——先把项目骨架跑起来。
- **环节 5：分模块开发**——按小任务逐段实现，并及时验证。
- **环节 6：自测与走查**——找出边界情况和潜在问题。
- **环节 7：集成联调**——把各模块串起来跑通完整流程。
- **环节 8：测试与验收**——对照最初需求，确认完成度。
- **环节 9：开发完成确认**——整理交付说明和已知限制。

## 环节 0：项目启动

> 主要和 AI 去聊天，将一个模糊的想法变成一个可执行的项目，而不是直接让 AI 写代码。

### 方法（执行清单）

**关键产出物**
- 一段清晰的项目「一句话定位」+ 几点初步想法（功能方向、目标人群、大致形态）

**具体动作**
- 你：把脑子里模糊的想法用自己的话讲出来，不用讲究逻辑和完整性
- AI：通过提问帮你理清"这个项目到底想解决什么问题"，引导你把模糊想法聚焦成可执行的方向，而不是立刻给方案或写代码

**结束标准（DoD）**
- 你能用一两句话说出"我想做一个什么样的东西，大概解决什么问题"
- 想法已经从"灵感"收敛成"可以进入需求澄清阶段"的状态

**可直接发给 AI 的 Prompt**

```text
我有一个模糊的想法,还没想清楚细节,请不要直接给方案或写代码。
先通过提问帮我理清楚:
1. 这个想法本质上是想解决什么问题
2. 大概是给谁用的
3. 现在最核心、最想先做出来的部分是什么
一步步引导我把这个想法聊清楚,聊完之后帮我总结成一句话定位。
```

### 案例补充（本项目证据）

#### 背景：为什么要 Coding？（项目总览 / OVERVIEW）

- **一句话记住**：**代码是工作流被理解之后的结果，不是项目的第一步。**
- **最初想法（决策日志 01）**：多模型答案对比评测器——输入问题、标准与多份回答，调用 DeepSeek 评测。
- **一句话定位**：把复制粘贴、逐份请求、结构校验、结果复核和排序固化成"可在本地运行的模型回答裁判器"。
- **想法来自已验证的手工流程**：Step 01–04 手工跑通后，重复劳动（复制粘贴、逐份请求、结果复核）成为产品化的理由——**已验证的手工流程成为产品需求**。

## 环节 1：需求澄清与范围确定

### 方法（执行清单）

**关键产出物**
- 一份「需求说明」文档（哪怕只有几段话）：要做什么、给谁用、核心场景是什么、明确不做什么

**具体动作**
- 你：用自己的话把想法讲清楚，哪怕模糊也先讲；明确"必须有"和"暂时不要"的功能边界
- AI：把你的口语化描述转成结构化需求（功能点列表 + 边界说明），并主动追问模糊点（而不是自己脑补）

**结束标准（DoD）**
- 你能一句话说清"这个项目做完是什么样子"
- AI 复述的需求和你脑子里想的一致，没有"AI 自己加戏"的功能

**可直接发给 AI 的 Prompt**

```text
请帮我把这个想法整理成结构化的需求说明,包括:
1. 核心功能点(列清单)
2. 目标用户是谁
3. 最核心的使用场景是什么
4. 明确列出"这一版先不做"的部分

将生成的文档存到项目根目录下的 `docs/*****需求文档.md`。
如果我的描述里有模糊、矛盾或者信息不够的地方,请直接指出来并追问我,
不要自己脑补细节替我做决定。
```

### 案例补充（本项目证据）

#### 裁判器的需求说明

- **项目证据：《需求说明》**——只做裁判器；删除出题器、后端、数据库等扩展。
- **PHASE A 需求清单（网页版"先把需求说清楚"）**：
  - 只做裁判器，不做出题器
  - 问题、标准、回答由用户手动粘贴
  - 支持多个"模型名称 + 回答"
  - 纯前端、本地使用、无数据库
  - 结构失败时保留原始返回，不自动修复
- **决策日志 03（范围纠偏）**：删除"出题器"扩展——用户明确第一版只做裁判器，项目不再继续扩大。
- **课堂方法提示**：先确定"做什么"，更要确定"不做什么"；AI 把口语想法整理成结构化需求，你检查它有没有加戏，并确认核心用户与核心场景。
- 需求清单是后续**环节 8 验收的依据**（逐条核对"完成/部分完成/不做"）。

#### 手工前置 1/3：先把"什么叫做对"定义清楚（STEP 01 准备规则）

> 这是在写代码前需求澄清的关键一步：检查用于生成评测题的提示词，删除冲突、隐藏要求和不稳定判断，得到一份可重复使用的评测生成模板。

- **阶段目标一句话**：**在写代码前，先把"什么叫做对"定义清楚。** 产出：一份边界清楚、能够被下一步直接使用的提示词模板。
- **原始目标（改写前）**："生成一道有明确区分度的模型评测题，以及与题目严格对应、可以稳定执行的二元评分标准。"
  - 对象：跨领域模型能力评测；交付：1 道题 + 12–18 个二元评分项；判定：每项只允许 0 或 1 分；约束：不依赖隐藏信息与整体印象。
- **关键定义（"稳定执行"）**：不同裁判仅依据原始问题、评分标准和待评回答，应能按照相同证据与判定步骤得到一致结果。

#### 手工前置 2/3：制造测试材料（STEP 02 准备测试）

> 这一步的作用不是“写出完美文案”，而是先把可评测的题目和评分标准定清楚。产出：一份可用于后续裁判的原始问题和 13 项二元评分标准。

- 先把抽象目标转成可观察的要求：例如“有网感”不直接评价，而是要求“首句有场景钩子、出现固定对比句式、评论区回复指定关键词、emoji 不超过 3 个”。
- 生成一个小红书文案任务，包含品牌、产品信息、目标人群、文案格式和禁止项。
- 同时配出 13 项二元评分标准，核心是“有没有明确证据”——只看回答里是否出现对应要求，而不是看整体感觉。

#### 手工前置 3/3：得到待评回答（STEP 03 准备回答）

> 把题目交给模型，得到一份可供后续裁判逐项检查的回答。这里的重点是：网页后面评测的是“用户粘贴进来的回答”，不是自动生成答案。

- 执行流程：题目 → 模型生成回答 → 得到待评文本。
- 这份回答会成为后续裁判的输入材料，包含可检查的事实、格式和互动要求。
- 这一步的意义不是“回答多好”，而是“答案已经稳定成可以被重复裁判的静态材料”。

## 环节 2：技术方案设计

### 方法（执行清单）

**关键产出物**
- 技术选型说明（用什么语言/框架/库，为什么）
- 简要架构图或文字描述（模块划分、数据怎么流转）
- 如果涉及数据存储：数据结构/表结构草图

**具体动作**
- AI：给出可行技术方案，说明取舍（不是直接甩一堆代码）
- 你：审核方案是否匹配你的能力（能不能维护）、是否匹配项目体量（别小项目上重架构）

**如果 AI 给的方案你看不懂，怎么办**（不要假装懂了直接往下走，这是后面失控的最大源头之一）
- 直接跟 AI 说："用大白话/打比方跟我解释一遍，不要用专业术语"
- "假设我是完全不懂技术的人，你要怎么跟我讲清楚这个方案在做什么"
- "有没有更简单、但够用的方案？哪怕性能/扩展性差一点也没关系"
- "这个技术我以后自己改代码的时候，最容易在哪里踩坑?"
- 判断标准：如果 AI 解释完，你还是没法用自己的话复述一遍"这个方案大概是怎么回事"，说明还没讲清楚，继续追问，别往下走
- 遇到绕不开的专业名词（比如某个框架、某种架构模式），让 AI 用你熟悉的东西打比方（生活场景、你已经会的其他工具），而不是用另一个你也不懂的术语解释一个术语

**结束标准（DoD）**
- 你能看懂并解释"为什么选这个方案"，而不是"AI说了算，我不懂"
- 方案里没有你完全陌生、且 AI 也没解释清楚的黑盒技术

**可直接发给 AI 的 Prompt**

```text
基于以上确定的需求,请给我可行的技术方案。

对每个方案请说明:
1. 技术选型说明(用什么语言/框架/库,为什么)
2. 简要架构图或文字描述(模块划分、数据怎么流转)
3. 如果涉及数据存储:数据结构/表结构草图
4. 大致用什么技术/工具(不用列太细)
5. 优缺点和取舍是什么
6. 用大白话/打比方讲清楚这个方案是在做什么,不要堆专业术语

将生成的文档存到项目根目录下的 `docs/*****技术方案.md`。
最后请告诉我这个方案里有没有"我以后自己改代码时特别容易踩坑"的地方。
```

### 案例补充（本项目证据）

- **项目证据：《技术选型与架构说明》**——原生 HTML / CSS / JS；纯前端；无构建、无数据库。


## 环节 3：任务拆解与排期

### 方法（执行清单）

**关键产出物**
- 一份任务清单（Task List）：按模块/功能拆成可独立验收的小任务，每个任务能在一次对话/一个 commit 内完成

**具体动作**
- AI：把大需求拆成小任务，标注任务间的依赖关系（哪个必须先做）
- 你：检查拆分粒度是否合理——太大你就没法中途检查，太碎会失去整体感

**结束标准（DoD）**
- 每个任务都有清晰的"验收方式"（比如"这个函数输入A输出B""这个页面能看到X"）
- 你知道接下来要按什么顺序推进，不是走一步看一步

**可直接发给 AI 的 Prompt**

```text
请把我们确定的方案拆解成一个具体的任务清单。

要求:
1. 每个任务要足够小,能在一次对话/一次提交里做完
2. 标注任务之间的先后依赖关系(哪个必须先做完才能做下一个)
3. 每个任务都附上"怎么算这个任务做完了"的验收标准
   (要具体到我能亲自操作验证,比如"打开某页面应该看到什么"
   或"调用某个函数输入什么应该输出什么")

将生成的文档存到项目根目录下的 `docs/*****任务清单.md`。
请按顺序编号列出。
```

### 案例补充（本项目证据）

- **项目证据：《任务清单》M1–M9**——每项可在一次对话 / 一个 commit 内完成。
- **文档链（需求层层落实）**：01 需求说明 → 02 技术与架构 → 03 任务清单。
- **M1–M9 增量交付清单**（每一轮都能单独验收）：

| 里程碑 | 内容 | 说明 |

| M2 | 问题与标准 | 长文本录入与空值校验 |
| M3 | 多份回答 | 新增 / 删除 / 标签切换 |

## 环节 4：环境搭建与脚手架

### 方法（执行清单）

**关键产出物**
- 可运行的项目骨架（能启动、能看到空白页面/接口返回200）
- 目录结构说明

**具体动作**
- AI：搭建项目结构，配置好基础依赖
- 你：亲自跑一遍启动命令，确认在你自己的机器上真的能跑起来（不是只在 AI 的描述里能跑）

**结束标准（DoD）**
- 项目在你本地成功启动，没有报错
- 你理解目录结构里"哪个文件夹放什么"的基本逻辑

**可直接发给 AI 的 Prompt**

```text
请帮我搭建这个项目的基础脚手架(目录结构 + 必要依赖),先不用写业务逻辑。

完成后请告诉我:
1. 目录结构里每个主要文件夹/文件是干嘛的(简单一句话说明)
2. 我需要在终端里依次敲哪些命令,才能把项目跑起来
3. 跑起来之后,我应该在浏览器/终端里看到什么,
   才能确认"搭建成功了"
```

### 案例补充（本项目证据）

- **项目证据：M1 基础页面**——`index.html` + `styles.css` + `app.js`，可直接本地打开（纯静态，无需构建）。
- **骨架内容**：输入区 / 结果区 / 空状态（空状态是页面"名词"与区域的第一版雏形）。
- **打开方式**：直接打开 `index.html`，或在本目录启动任意静态文件服务器。
- **方法印证**：先让最小骨架在自己的机器上跑起来——AI 搭结构，你亲自打开、刷新、查看错误，并理解每个文件承担什么职责。

## 环节 5：分模块开发实现

### 方法（执行清单）

**关键产出物**
- 按环节 3 的任务清单，逐个交付的功能代码（每次一个小任务，而不是一次性甩一大坨）

**具体动作**
- AI：每次只做一个约定好的小任务，做完主动说明"改了什么文件、实现了什么逻辑"
- 你：**每个小任务做完后立刻验证**，不要攒到最后一起看（这是最容易失控的环节）

**结束标准（DoD）**
- 当前任务对应的功能，你亲自验证过（跑起来看、点一下按钮、发个请求），确实符合预期
- 没有"AI 说做完了，但我没看"的任务

**可直接发给 AI 的 Prompt**

```text
现在请只完成任务清单里的【任务X:具体任务名】,不要顺带做其他任务。
每次执行一个任务并进行验证,待验证通过后提交一个commit后再开始下一个任务,
不要一次性做完所有任务再验证。

每一步做完之后请告诉我:
1. 改动了哪些文件(简单列出,不用贴全部代码)
2. 每处改动实现了什么逻辑(用大白话说)
3. 需要我验证的告诉我应该怎么操作才能验证这个任务确实做成了
   (具体到"打开哪个页面/敲哪条命令/点哪个按钮,应该看到什么结果")
```

### 案例补充（本项目证据）

- **项目证据：M2 → M8 逐项推进**——输入、回答、请求、解析、展示、排序分别交付；**不要让功能一次性堆满**，每轮都要求说明改了什么、怎样验收，再决定是否进入下一项。
- **网页 Step 05 的 PHASE B 印证**：先静态骨架，再输入、请求、解析、展示；根据真实使用反馈调整布局与标签页；最后补本地验证和开源安全检查。
- **代码证据（app.js 关键函数，来自 M4/M5 模块）**：

```javascript
function buildJudgeRequest(input, candidate) {
  return {
    model: "deepseek-v4-flash",
    messages: [
      { role: "system", content: JUDGE_SYSTEM_PROMPT },
      { role: "user", content: buildJudgeUserPrompt(input, candidate) },
    ],
    response_format: { type: "json_object" },
    stream: false,
  };
}

function buildJudgeJobs(input) {
  return input.candidates.map((candidate) => ({
    candidateId: candidate.id,
    modelName: candidate.modelName,
    request: buildJudgeRequest(input, candidate),
  }));
}
```

- **要点**：`buildJudgeJobs` 为每份回答生成独立请求（单回答单请求 + JSON 契约）；`response_format: json_object` 与 `stream: false` 是 M4"JSON 契约"的具体落地。
- **Git 记录证明模块演进**：M3 → M4 → M5 → M6 → M7 → M7.1 → M8 → M9。

## 环节 6：自测与代码走查

### 方法（执行清单）

**关键产出物**
- 关键逻辑的测试结果（哪怕是手动测试记录，不一定要写自动化测试）
- 一份"已知问题/边界情况"清单

**具体动作**
- AI：主动列出这段代码没覆盖到的边界情况、可能的 bug 点
- 你：挑几个边界场景（比如空输入、异常输入）亲自试一下，不要只测"正常路径"

**结束标准（DoD）**
- 正常场景和至少 1-2 个异常场景都手动验证过
- 已知的坑（哪怕暂时不修）你是清楚的，而不是"看起来能用就行"

**可直接发给 AI 的 Prompt**

```text
请针对刚才实现的【具体功能/模块名】,帮我做一次自查:

1. 列出这段代码可能没覆盖到的边界情况和潜在 bug 点
   (比如空输入、异常输入、极端值、网络失败等)
2. 针对每一条,给我具体的手动测试步骤,让我可以逐一验证
   (不需要写自动化测试代码,手动操作步骤就行)
3. 哪些问题你觉得现在必须修,哪些可以先记下来暂不处理
```

### 案例补充（本项目证据）

#### 手工前置 4/4：重复裁判验证（STEP 04 稳定性测试）

> 在编码之前，先用同一份材料手工验证"裁判标准是否稳定"——这正是自测走查精神的先行版，也是需求真实存在的证明。

- **阶段目标**：固定三项输入不变：Step 02 的原始问题与 13 项评分标准，以及 Step 03 的模型回答。观察重点不是文案好不好，而是**裁判能否重复得出相同结论**。
- **四轮独立裁判结果（RUN LOG）**：

| 轮次 | 得分 | 结果 | 标题汉字数 |
| --- | --- | --- | --- |
| ROUND 01 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |
| ROUND 02 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |
| ROUND 03 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 15 |
| ROUND 04 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |

- **稳定性结论（两层）**：
  - **稳定的核心结论 4/4**：四轮在最终分（12/13）、得分率（92%）和唯一失分项（C06）上完全一致。
  - **出现的局部漂移 14 ↔ 15**：第三轮对同一标题的汉字计数与其余三轮不同（15 vs 14），但都落在 14–20 的通过区间。
- **唯一失分项 C06 分析**：回答写的是"不是为了多复杂的步骤，是在进工位前……"，语义上形成了对比，但评分标准要求"不是"和"是"之间必须出现"……"或"..."。**逻辑满足，不等于字面格式满足**。四轮裁判都按严格字面条件记 0 分。
- **课堂观察：稳定性至少要分三层看**——只比较总分，会得到"裁判很稳定"；继续比较每项和理由，才会发现计数表述仍有漂移。**稳定性三层：总分 → 分项结论 → 证据与理由。**
- **四轮裁判共同结论汇总**：共同总分 12/13、92%；共同失分项 C06｜"不是……，是……"对比句式；共同直接证据"不是为了多复杂的步骤，是在进工位前……"；未触发事项（无红线规则、没有红线调整）；稳定性结论（总分、得分率、唯一失分项均一致）。
- **对项目的意义**：四轮稳定性测试负责**证明需求真实存在**；这个已验证的手工裁判流程成为 Step 05 的产品原型。

#### 代码层面的自测与走查

- **项目证据：M5 / M6 验证**——真实 API 通过；非 JSON、非法得分、缺失字段会被拒绝。
- **决策日志 04（失败策略）**：宁可暴露失败，也不伪造正常——非 JSON、漏字段或分数算不平时展示原始返回并要求人工复核（结构失败时保留原始返回，不自动修复）。
- **验证覆盖的异常路径**：空输入、非法 JSON、异常分数、网络失败（超时/错误状态）。
- **方法印证**：正常路径能用，只代表测试刚刚开始——AI 列边界与潜在 bug，你亲自试空输入、非法 JSON、异常分数、网络失败等异常路径。

**结束标准（DoD）**

### 案例补充（本项目证据）

- **项目证据：完整评测路径**——粘贴材料 → 多回答 → 发起裁判 → 结果标签 → 排名。
- **项目代码数据流（各模块串起来的接口）**：

```
INPUT（表单与回答标签：读取并校验用户输入）
→ BUILD（buildJudgeJobs：每份回答生成独立请求）
→ REQUEST（requestDeepSeek：fetch + 超时 + 错误处理）
→ PARSE（parseJudgeResponse：拒绝非法或矛盾结果）
→ OUTPUT（rank + render：排序、标签与逐项证据）
```

- **代码阅读方法（教学要点）**：面对 1200 多行的 `app.js`，不要按文件长度产生恐惧。沿着一次用户操作追踪即可：**填写 → 校验 → 构造任务 → 发请求 → 解析 → 排名 → 渲染**。每个函数都是前面任务清单中某个小任务的代码化结果。
- **联调中的输入数据来自环节 1 的手工材料**：Step 02 的题目与 13 项标准、Step 03 的回答，正是联调时粘贴进网页的"问题 / 评分标准 / 回答"样例。

## 环节 8：测试与验收

### 方法（执行清单）

**关键产出物**
- 对照环节 1 的需求清单，逐条打勾的验收结果
- 遗留问题清单（哪些是这一版不修的，明确记下来而不是遗忘）

**具体动作**
- 你：拿着最初的需求清单，一条条核对是否做到
- AI：协助定位任何"做出来但不符合预期"的问题根因

**结束标准（DoD）**
- 需求清单里的每一条，状态是"完成/部分完成/不做"，而不是"不确定"
- 你敢把这个版本给别人用，而不是心里没底

**可直接发给 AI 的 Prompt**

```text
这是我们最初环节1确定的需求清单:
[把环节1的需求清单粘贴到这里]

请逐条核对当前代码是否满足,并标注每一条的状态:
完成 / 部分完成 / 未做

对于"部分完成"或"未做"的条目,请说明原因,
以及不做/没做完会有什么实际影响。
```

### 案例补充（本项目证据）

- **项目证据：布局与结果微调**——样式简化、左右布局、回答标签、结果标签均来自验收反馈。
- **反馈循环四条（代码完成过程中，界面被真实反馈改写）**：

| 反馈 | 具体内容 |
| --- | --- |
| 视觉收敛 | "样式太复杂了"——页面从装饰性设计改为白底、单栏、弱边框的本地工具风格 |
| 空间重组 | 输入与回答左右布局——左侧放问题和标准，右侧放待评回答；窄屏自动回到单栏 |
| 多回答交互 | 用标签切换回答——避免多份长回答同时纵向堆叠，错误时还能自动跳转到对应标签 |
| 结果微调 | 用模型标签切换结果——每次只看一个模型的完整结果，同时保留失败结果和键盘导航 |

- **验收态度**：不要凭"看起来差不多"结束。每项都应是完成、部分完成或明确不做，并记录遗留问题。
- **最终验收结果（对照环节 1 的需求清单）**：
  - **最终做到了**：输入原始问题与评分标准；手动录入并切换多份回答；独立调用裁判并处理请求状态；严格解析 JSON 展示逐项证据；前端排序、并列名次与失败隔离。
  - **明确没有做**：出题器或自动生成回答；登录、后端、数据库和历史记录；复杂自动修复或多轮纠错；题库、批量导入导出与报表；在安全处理前直接公开 Git 历史。
- **验收正确性来自环节 1 定义的材料**：13 项评分标准（C01–C13）就是验收"裁判结果是否正确"的对照清单，四轮重复裁判结论（环节 6）为验收提供基准值。

**关键产出物**

**具体动作**

**结束标准（DoD）**
- 即使过一个月你回来看这份说明，也能知道当时做到了哪一步

- **安全教训（功能完成，不等于可以直接开源）**：
  - M9 检查确认：当前 `config.js` 已被 Git 忽略、待提交文件未发现本地 Key；

- **本步产出**：可在本地运行的模型回答裁判器 + 开源前检查清单——从手工流程到可复用工具 ✓
- **方法印证**：最终代码之外，还要留下可恢复的项目状态——AI 整理怎么运行、做了什么、没做什么；你确认说明与真实状态一致，未来能接着维护。

## 贯穿全流程的一条原则

**AI 交付节奏 vs 你的验证节奏要匹配**——AI 天然倾向于一口气多做，你需要主动"喊停"、分批验证。之前项目不理想，大概率就出在环节 5-6：AI 一次产出太多，你没能逐块验证，问题堆积到后面才爆发。

### 案例补充（本项目证据）

- 网页 Step 05 的推进方式（"开始 M2 / M3 / … / M9"）本质上是在控制风险：**上一块没有看懂、没有验证，就不进入下一块。**
- **课堂观察（人机分工）**：这次 Vibe Coding 的核心不是"AI 写了多少代码"，而是**人持续负责方向、取舍和验收，AI 负责结构化、实现、解释和暴露风险**。只有双方职责清楚，"会聊天"才会变成"会 Coding"。
- 网页九环节的四个问题（与执行清单定位一致）：**产出物是什么 / AI 做什么 / 你做什么 / 什么算完成**。

# 第三部分：项目复盘与课堂总结

---

## 可重复的 Coding 方法（五层倒序）

1. **05 交付说明与安全收尾**——知道现在做到哪里
2. **04 联调、测试与需求验收**——亲自跑通完整路径
3. **03 分模块实现与即时验证**——一次只交付一个任务
4. **02 技术方案与任务清单**——知道为什么这样做
5. **01 需求澄清与范围边界**——先决定做什么、不做什么

## 核心方法论总结

- AI 可以快速写代码，但**你要控制方向、范围、节奏和验收**。
- 每一轮都留下明确产出，每一个小任务都立刻验证。
- 最终得到的才不是"一堆 AI 生成代码"，而是一个**你理解、敢用、能继续维护的项目**。

## 课堂主线（课程结束时你应该会自己推进项目）

- 这个案例覆盖了从模糊想法到本地可运行网页的完整 Coding 路径。
- **四轮稳定性测试负责证明需求真实存在；九环协作清单和 M1–M9 才是本课程的核心方法。**
- 课堂主线公式：`定义质量 → 制造测试 → 生成回答 → 验证稳定 → 编码工具`
- 下一项目复用指令：以 Step 05 为教学主线，复用"需求澄清 → 技术方案 → 任务拆解 → 分模块实现 → 自测 → 联调 → 验收 → 交付"的方法推进下一个 Web Coding 项目。

## 附：网页交互功能（script.js）

- **章节导航高亮**：滚动时按当前视口位置（`scrollY + 视口高度 × 32%`）判断当前章节，高亮侧边导航。
- **阅读进度条**：侧边栏竖向进度条随滚动比例增长。
- **改造前后切换**：Step 01 的"改造前 / 改造后"分段按钮切换对应面板。
- **复制按钮**：一键复制模型回答全文（`data-copy-target`）或预设指令文本（`data-copy-text`），成功/失败均有 Toast 提示（"已复制" / "复制失败，请手动选择"）。
