## 环节 0：项目启动

> 主要和 AI 去聊天，将一个模糊的想法变成一个可执行的项目，而不是直接让 AI 写代码。

### 方法（执行清单）

**关键产出物**
- 一段清晰的项目「一句话定位」+ 几点初步想法（功能方向、目标人群、大致形态）

**具体动作**
- 你：把脑子里模糊的想法用自己的话讲出来，不用讲究逻辑和完整性
- AI：通过提问帮你理清"这个项目到底想解决什么问题"，引导你把模糊想法聚焦成可执行的方向，而不是立刻给方案或写代码

**结束标准（DoD）**
- 你能用一两句话说出"我想做一个什么样的东西，大概解决什么问题"
- 想法已经从"灵感"收敛成"可以进入需求澄清阶段"的状态

**可直接发给 AI 的 Prompt**

```text
我有一个模糊的想法,还没想清楚细节,请不要直接给方案或写代码。
先通过提问帮我理清楚:
1. 这个想法本质上是想解决什么问题
2. 大概是给谁用的
3. 现在最核心、最想先做出来的部分是什么
一步步引导我把这个想法聊清楚,聊完之后帮我总结成一句话定位。
```

### 案例补充（本项目证据）

#### 背景：为什么要 Coding？（项目总览 / OVERVIEW）

- **课堂主线**：**定义质量 → 制造测试 → 生成回答 → 验证稳定 → 编码工具**。
- **核心论点**：前四步（01—04）用来解释为什么需要这个工具；真正的主体是 Step 05：怎样澄清需求、选择方案、拆解任务，到逐模块实现、亲自验证、联调验收与交付收尾。
- **一句话记住**：**代码是工作流被理解之后的结果，不是项目的第一步。**
- **关键数字**：

| 数字 | 含义 |
| --- | --- |
| 4/4 | 重复裁判核心结论一致 |
| 9 | 个 Web Coding 环节 |
| 9 | 个增量开发任务（M1–M9） |
| 5 | 个最终项目文件 |

- **五步流水线（每一步的产出成为下一步输入）**：
  1. **01 审查 + 改写（INPUT）**：初版元提示词 → 目标正确，但部分规则互相拉扯，可能导致 AI 为了满足格式而硬凑内容。产出：改写后的模板。
  2. **02 实例化模板（TRANSFORM）**：题目 + 评分标准 → 将抽象的"内容网感"转换为可静态检查的任务约束和 13 个二元评分项。产出：题目成为模型输入。
  3. **03 执行任务（OUTPUT）**：小红书文案 → 模型依据明确题目生成答案；答案本身就是之后执行 AI 评分的待评对象。产出：回答与标准一起成为裁判输入。
  4. **04 验证稳定性（VERIFY）**：重复裁判结果 → 重复提交完全相同的题目、标准和回答，观察总分、失分项与理由是否保持一致。产出：已验证的手工流程成为产品需求。
  5. **05 Vibe Coding（PRODUCTIZE）**：模型回答裁判器 → 把复制粘贴、逐份请求、结构校验、结果复核和排序固化成一个本地网页。
- **课堂观察**：前三步建立"定义质量 → 制造测试 → 运行被测对象"；第四步验证裁判是否稳定；第五步才把流程写成工具。

#### 本项目的一步定位与起点

- **最初想法（决策日志 01）**：多模型答案对比评测器——输入问题、标准与多份回答，调用 DeepSeek 评测。
- **一句话定位**：把复制粘贴、逐份请求、结构校验、结果复核和排序固化成"可在本地运行的模型回答裁判器"。
- **想法来自已验证的手工流程**：Step 01–04 手工跑通后，重复劳动（复制粘贴、逐份请求、结果复核）成为产品化的理由——**已验证的手工流程成为产品需求**。

## 环节 1：需求澄清与范围确定

### 方法（执行清单）

**关键产出物**
- 一份「需求说明」文档（哪怕只有几段话）：要做什么、给谁用、核心场景是什么、明确不做什么

**具体动作**
- 你：用自己的话把想法讲清楚，哪怕模糊也先讲；明确"必须有"和"暂时不要"的功能边界
- AI：把你的口语化描述转成结构化需求（功能点列表 + 边界说明），并主动追问模糊点（而不是自己脑补）

**结束标准（DoD）**
- 你能一句话说清"这个项目做完是什么样子"
- AI 复述的需求和你脑子里想的一致，没有"AI 自己加戏"的功能

**可直接发给 AI 的 Prompt**

```text
请帮我把这个想法整理成结构化的需求说明,包括:
1. 核心功能点(列清单)
2. 目标用户是谁
3. 最核心的使用场景是什么
4. 明确列出"这一版先不做"的部分

将生成的文档存到项目根目录下的 `docs/*****需求文档.md`。
如果我的描述里有模糊、矛盾或者信息不够的地方,请直接指出来并追问我,
不要自己脑补细节替我做决定。
```

### 案例补充（本项目证据）

#### 裁判器的需求说明

- **项目证据：《需求说明》**——只做裁判器；删除出题器、后端、数据库等扩展。
- **PHASE A 需求清单（网页版"先把需求说清楚"）**：
  - 只做裁判器，不做出题器
  - 问题、标准、回答由用户手动粘贴
  - 支持多个"模型名称 + 回答"
  - 纯前端、本地使用、无数据库
  - 结构失败时保留原始返回，不自动修复
- **决策日志 03（范围纠偏）**：删除"出题器"扩展——用户明确第一版只做裁判器，项目不再继续扩大。
- **课堂方法提示**：先确定"做什么"，更要确定"不做什么"；AI 把口语想法整理成结构化需求，你检查它有没有加戏，并确认核心用户与核心场景。
- 需求清单是后续**环节 8 验收的依据**（逐条核对"完成/部分完成/不做"）。

#### 手工前置 1/3：先把"什么叫做对"定义清楚（STEP 01 准备规则）

> 这是在写代码前需求澄清的关键一步：检查用于生成评测题的提示词，删除冲突、隐藏要求和不稳定判断，得到一份可重复使用的评测生成模板。

- **阶段目标一句话**：**在写代码前，先把"什么叫做对"定义清楚。** 产出：一份边界清楚、能够被下一步直接使用的提示词模板。
- **原始目标（改写前）**："生成一道有明确区分度的模型评测题，以及与题目严格对应、可以稳定执行的二元评分标准。"
  - 对象：跨领域模型能力评测；交付：1 道题 + 12–18 个二元评分项；判定：每项只允许 0 或 1 分；约束：不依赖隐藏信息与整体印象。
- **发现的核心矛盾**：**规则 A："必须有 12–18 项" VS 规则 B："不得重复或隐藏要求"**——对简单主题而言，可验证的独立要求可能不足 12 个。若强制凑数，模型就可能拆得过细，甚至偷偷加入题目没有要求的偏好。
- **审查的六大发现（审查不是挑语病，而是寻找会让系统失稳的规则）**：
  1. **评分项数量硬约束**：固定 12–18 项会诱发"为了数量而设计"，与原子化、无隐藏要求产生冲突。【优先修正】
  2. **重复扣分边界含糊**："同一缺陷不得重复扣分"要求裁判追溯根因，不同 AI 可能得到不同解释。【稳定性风险】
  3. **设计方式强制组合**：要求每道题至少使用两种设计手法，可能迫使窄任务添加不必要的取舍。【形式主义】
  4. **工具输出不可复现**：即使允许联网或运行代码，裁判环境也未必能重现当时版本与结果。【环境漂移】
  5. **"原样包含"的冲突**：规则要求固定文本原样输出，同时又要求替换评分项数量与满分。【指令冲突】
  6. **输入缺失没有出口**：主题为空或过宽时，模型缺少明确的停止条件，容易擅自补全核心任务。【失败路径】
- **关键改造示例（改造前 vs 改造后）**：
  - 改造前："每个关键缺陷只能影响最相关的一个评分项，不得重复扣分。"——问题：裁判必须判断多个失败是否来自"同一个根因"，这不是稳定的静态文本判断。
  - 改造后："不同评分项只要检查的是不同原子结果，就分别根据各自证据判定。"——思路：不追溯根因，只检查可观察结果；评分项设计阶段负责避免两个项目检查同一事实。
- **改写后的元提示词八个部分**（默认评分环境明确为"只看原始问题、评分标准和待评回答的静态文本判定"）：
  1. **输入配置**：增加"评分执行环境"，信息不足时只请求最少补充。
  2. **内部设计流程**：先建立题目要求与评分项的一一映射，并用边界样例测试。
  3. **题目生成要求**：写清工具边界、数据快照、运行环境和静态证据。
  4. **二元评分标准**：按难度设置数量范围，不为凑数添加隐藏要求。
  5. **评分项固定结构**：加入判定依据、接受的等价形式与归属边界。
  6. **红线规则**：最多两条；触发后仍给出全部原始项得分。
  7. **计分与裁判规则**：15 条固定规则统一证据、冲突与得分处理。
  8. **静默自检与输出格式**：输出前检查映射、数量、容差和满分一致性。
- **关键定义（"稳定执行"）**：不同裁判仅依据原始问题、评分标准和待评回答，应能按照相同证据与判定步骤得到一致结果。

#### 手工前置 2/3：制造测试材料（STEP 02 准备测试）

> 用模板生成一份小红书文案任务和对应评分标准。它们之后会成为裁判网页里的"问题"和"评分标准"输入。一句话记住：**先有稳定的测试材料，网页才知道应该评什么。** 产出：原始问题 + 13 项二元评分标准。

- **输入配置**：

| 配置项 | 取值 |
| --- | --- |
| 评测领域 | 写作 |
| 重点能力 | 内容网感 |
| 难度 | 较难 |
| 使用场景 | 小红书营销文案 |
| 评分环境 | 静态文本判定 |
| 额外要求 | 符合平台内容风格 |

- **核心方法论：把主观目标翻译成可观察信号**——"有网感"很主观，怎样变成二元判定？把每个抽象目标转换为题目中的**可观察信号**与**静态判定方式**：

| 抽象目标 | 题目中的可观察信号 | 判定方式 |
| --- | --- | --- |
| 开头有抓力 | 首句以"谁懂"开头，并出现"电梯" | 检索位置与词语 |
| 具有生活场景 | 具体时间点与出门 / 电梯 / 工位同句 | 检查格式与共现 |
| 网络化表达 | 使用"不是……，是……"与"救命" | 检查句式和语境 |
| 可带动互动 | 要求评论区回复原样关键词"通勤" | 检查动作与关键词 |
| 平台风格克制 | 禁用五个夸张词，emoji 不超过 3 个 | 全文检索与计数 |

- **生成的题目（虚构品牌「晚八点」）**：产品锁：容量 15mL；香型 白茶 / 雪松 / 无花果；价格 39元；使用方式 出门前喷衣领或围巾。任务：为早高峰通勤、在电梯或工位前想快速整理状态的人，写一篇严格按"标题 / 正文 / 话题"交付的小红书笔记。部分题目约束：标题 14–20 个汉字；首句"谁懂"；具体时间点；评论关键词"通勤"；最多 3 个 emoji；仅 3 个固定话题。
- **13 项二元评分标准（静态验收清单）**：

| 编号 | 评分项 | 类别 |
| --- | --- | --- |
| C01 | 三段式交付结构 | 结构 |
| C02 | 标题上班与长度 | 标题 |
| C03 | 首句场景钩子 | 文案 |
| C04 | 目标通勤人群 | 受众 |
| C05 | 时间点具体场景 | 场景 |
| C06 | 对比句式 | 表达 |
| C07 | "救命"的语境 | 表达 |
| C08 | 产品事实完整 | 事实 |
| C09 | 评论互动引导 | 互动 |
| C10 | 出门前喷洒动作 | 用法 |
| C11 | 禁用营销词规避 | 限制 |
| C12 | emoji 数量上限 | 格式 |
| C13 | 固定三话题 | 话题 |

- **评分标准的关键原文原则**：
  - **题目中的边界**："不得补充留香时长、功效、成分、安全性、销量、折扣或用户反馈等未提供信息。"
  - **评分的证据原则**："只有回答中存在满足该项'1分条件'的明确证据时才能记1分。"
  - **冲突处理**："同一检查对象出现互相冲突的内容且没有明确最终修正版本时，相关评分项记0分。"
  - **等价形式**："15 ml""15ML"可等价于"15mL"；"39 元"可等价于"39元"。
  - **未设红线规则的原因**：普通漏项、表达问题或单个事实错误，都可以由对应的二元评分项处理，不需要把总分直接归零。
- **课堂观察**：这里并没有真正"客观测量审美"。它测量的是一组被预先定义、与平台文案风格相关的可观察行为。**可复现性提高了，但测量范围也被明确收窄了。**

#### 手工前置 3/3：得到待评回答（STEP 03 准备回答）

> 把原始问题交给模型，得到一份真实回答。至此，裁判流程所需的"问题、标准、回答"三项材料全部准备完成。一句话记住：**网页不是生成回答，而是评测用户粘贴进来的回答。** 产出：一份可供重复裁判的静态模型回答。

- **执行流程**：INPUT：Step 02 原始问题（产品事实 + 文案要求 + 禁止项）→ MODEL：生成回答（不联网 · 不调用工具）→ OUTPUT：待评小红书文案（之后可交给 AI 裁判评分）。
- **示例回答（全文）**：
  - **标题**：上班前给通勤状态按下整理键呀
  - **正文**：谁懂，8:20出门赶进电梯前，通勤状态乱糟糟真的救命。出门前在衣领喷一下「晚八点」通勤香氛喷雾，15mL，白茶、雪松、无花果三种香型，39元。不是为了多复杂的步骤，是在进工位前，给自己一个快速整理状态的小动作。你通勤时会选哪种香型？评论区回复"通勤"一起聊聊。
  - **话题**：#通勤好物　#上班状态　#香氛分享
- **回答留下的可评分直接证据**：
  - `8:20 + 出门 + 电梯`：一个句子同时留下时间格式与通勤场景证据。
  - `15mL / 三种香型 / 39元`：题内允许的产品事实被直接写入交付内容。
  - `不是…，是…`：模型使用了要求的对比逻辑，但采用单个省略号字符"…"；是否被 C06 接受，应由后续裁判严格按评分标准判定。
  - `评论区回复"通勤"`：互动动作、位置和指定关键词同时可见。
- **事实边界**：本页面没有执行正式评分，因此不声称该回答获得多少分。可以确认的是：回答已经成为一个可供下一阶段裁判逐项检查的静态对象。特别是 C06 对省略号形式有精确要求，是否通过不能凭整体观感代替逐项判定。
- **输入与输出边界**：模型看到了——完整产品事实；目标人群与使用场景；标题、正文、话题格式；所有必须项与禁止项。模型没有看到——13 个评分项的编号；每项的具体判定文字；任何标准答案或参考解法；后续裁判的评分结果。

## 环节 2：技术方案设计

### 方法（执行清单）

**关键产出物**
- 技术选型说明（用什么语言/框架/库，为什么）
- 简要架构图或文字描述（模块划分、数据怎么流转）
- 如果涉及数据存储：数据结构/表结构草图

**具体动作**
- AI：给出可行技术方案，说明取舍（不是直接甩一堆代码）

```javascript
function buildJudgeRequest(input, candidate) {
  return {
    model: "deepseek-v4-flash",
    messages: [
      { role: "system", content: JUDGE_SYSTEM_PROMPT },
      { role: "user", content: buildJudgeUserPrompt(input, candidate) },
    ],
    response_format: { type: "json_object" },
    stream: false,
  };
}

function buildJudgeJobs(input) {
  return input.candidates.map((candidate) => ({
    candidateId: candidate.id,
    modelName: candidate.modelName,
    request: buildJudgeRequest(input, candidate),
  }));
}
```

- **要点**：`buildJudgeJobs` 为每份回答生成独立请求（单回答单请求 + JSON 契约）；`response_format: json_object` 与 `stream: false` 是 M4"JSON 契约"的具体落地。

### 案例补充（本项目证据）

#### 手工前置 4/4：重复裁判验证（STEP 04 稳定性测试）

> 在编码之前，先用同一份材料手工验证"裁判标准是否稳定"——这正是自测走查精神的先行版，也是需求真实存在的证明。

- **阶段目标**：固定三项输入不变：Step 02 的原始问题与 13 项评分标准，以及 Step 03 的模型回答。观察重点不是文案好不好，而是**裁判能否重复得出相同结论**。
- **四轮独立裁判结果（RUN LOG）**：

| 轮次 | 得分 | 结果 | 标题汉字数 |
| --- | --- | --- | --- |
| ROUND 01 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |
| ROUND 02 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |
| ROUND 03 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 15 |
| ROUND 04 | 12/13 | C06 = 0；其余 12 项通过；得分率 92% | 14 |

- **稳定性结论（两层）**：
  - **稳定的核心结论 4/4**：四轮在最终分（12/13）、得分率（92%）和唯一失分项（C06）上完全一致。
  - **出现的局部漂移 14 ↔ 15**：第三轮对同一标题的汉字计数与其余三轮不同（15 vs 14），但都落在 14–20 的通过区间。
- **唯一失分项 C06 分析**：回答写的是"不是为了多复杂的步骤，是在进工位前……"，语义上形成了对比，但评分标准要求"不是"和"是"之间必须出现"……"或"..."。**逻辑满足，不等于字面格式满足**。四轮裁判都按严格字面条件记 0 分。
- **课堂观察：稳定性至少要分三层看**——只比较总分，会得到"裁判很稳定"；继续比较每项和理由，才会发现计数表述仍有漂移。**稳定性三层：总分 → 分项结论 → 证据与理由。**
- **四轮裁判共同结论汇总**：共同总分 12/13、92%；共同失分项 C06｜"不是……，是……"对比句式；共同直接证据"不是为了多复杂的步骤，是在进工位前……"；未触发事项（无红线规则、没有红线调整）；稳定性结论（总分、得分率、唯一失分项均一致）。
- **对项目的意义**：四轮稳定性测试负责**证明需求真实存在**；这个已验证的手工裁判流程成为 Step 05 的产品原型。

#### 代码层面的自测与走查

- **项目证据：M5 / M6 验证**——真实 API 通过；非 JSON、非法得分、缺失字段会被拒绝。
- **决策日志 04（失败策略）**：宁可暴露失败，也不伪造正常——非 JSON、漏字段或分数算不平时展示原始返回并要求人工复核（结构失败时保留原始返回，不自动修复）。

**结束标准（DoD）**
- 需求清单里的每一条，状态是"完成/部分完成/不做"，而不是"不确定"
- 你敢把这个版本给别人用，而不是心里没底

**可直接发给 AI 的 Prompt**

```text
这是我们最初环节1确定的需求清单:
[把环节1的需求清单粘贴到这里]

请逐条核对当前代码是否满足,并标注每一条的状态:
完成 / 部分完成 / 未做

对于"部分完成"或"未做"的条目,请说明原因,
以及不做/没做完会有什么实际影响。
```

### 案例补充（本项目证据）

- **项目证据：布局与结果微调**——样式简化、左右布局、回答标签、结果标签均来自验收反馈。
- **反馈循环四条（代码完成过程中，界面被真实反馈改写）**：

| 反馈 | 具体内容 |
| --- | --- |
| 视觉收敛 | "样式太复杂了"——页面从装饰性设计改为白底、单栏、弱边框的本地工具风格 |
| 空间重组 | 输入与回答左右布局——左侧放问题和标准，右侧放待评回答；窄屏自动回到单栏 |
| 多回答交互 | 用标签切换回答——避免多份长回答同时纵向堆叠，错误时还能自动跳转到对应标签 |
| 结果微调 | 用模型标签切换结果——每次只看一个模型的完整结果，同时保留失败结果和键盘导航 |

- **验收态度**：不要凭"看起来差不多"结束。每项都应是完成、部分完成或明确不做，并记录遗留问题。
- **最终验收结果（对照环节 1 的需求清单）**：
  - **最终做到了**：输入原始问题与评分标准；手动录入并切换多份回答；独立调用裁判并处理请求状态；严格解析 JSON 展示逐项证据；前端排序、并列名次与失败隔离。
  - **明确没有做**：出题器或自动生成回答；登录、后端、数据库和历史记录；复杂自动修复或多轮纠错；题库、批量导入导出与报表；在安全处理前直接公开 Git 历史。
- **验收正确性来自环节 1 定义的材料**：13 项评分标准（C01–C13）就是验收"裁判结果是否正确"的对照清单，四轮重复裁判结论（环节 6）为验收提供基准值。

## 环节 9：开发完成确认（交付前收尾）

### 方法（执行清单）

**关键产出物**
- 最终代码 + 一份简要说明（怎么运行、有什么已知限制）

**具体动作**
- AI：整理一份"这个版本做了什么、没做了什么、怎么跑"的总结
- 你：通读一遍，确认这份总结和你的理解一致

**结束标准（DoD）**
- 即使过一个月你回来看这份说明，也能知道当时做到了哪一步
- 项目状态是"我清楚现在的样子"，而不是"AI 说做完了我就信了"

**可直接发给 AI 的 Prompt**

```text
请帮我整理一份这个版本的总结文档,包括:

1. 这个版本做了哪些功能(简明列出)
2. 有哪些已知限制或还没做完的部分
3. 怎么运行这个项目(命令 + 步骤)
4. 如果我以后要接着改这个项目,有什么需要特别注意的地方
   (比如容易踩坑的模块、临时方案以后要替换的地方等)
```

### 案例补充（本项目证据）

- **项目证据：M9 README + 开源检查**——使用说明、边界、验证记录、Key 与 Git 历史风险。
- **安全教训（功能完成，不等于可以直接开源）**：
  - M9 检查确认：当前 `config.js` 已被 Git 忽略、待提交文件未发现本地 Key；
  - **但历史扫描发现旧提交中的 `app.js` 曾包含真实 Key**；
  - 因此发布前必须先**轮换旧 Key**，并**清理 Git 历史或从脱敏文件建立全新仓库**。
- **已记录的验证状态汇总**：M5 真实 API 请求由项目所有者确认通过；M6 解析测试通过；JavaScript 语法、非法得分、非 JSON、缺失字段和并列排名已有本地检查。
- **本步产出**：可在本地运行的模型回答裁判器 + 开源前检查清单——从手工流程到可复用工具 ✓
- **方法印证**：最终代码之外，还要留下可恢复的项目状态——AI 整理怎么运行、做了什么、没做什么；你确认说明与真实状态一致，未来能接着维护。

## 贯穿全流程的一条原则

**AI 交付节奏 vs 你的验证节奏要匹配**——AI 天然倾向于一口气多做，你需要主动"喊停"、分批验证。之前项目不理想，大概率就出在环节 5-6：AI 一次产出太多，你没能逐块验证，问题堆积到后面才爆发。

### 案例补充（本项目证据）

- 网页 Step 05 的推进方式（"开始 M2 / M3 / … / M9"）本质上是在控制风险：**上一块没有看懂、没有验证，就不进入下一块。**
- **课堂观察（人机分工）**：这次 Vibe Coding 的核心不是"AI 写了多少代码"，而是**人持续负责方向、取舍和验收，AI 负责结构化、实现、解释和暴露风险**。只有双方职责清楚，"会聊天"才会变成"会 Coding"。
- 网页九环节的四个问题（与执行清单定位一致）：**产出物是什么 / AI 做什么 / 你做什么 / 什么算完成**。

## 2.1 初始化项目文档

**Prompt**：

```text
请先完整阅读当前项目，然后自动整理项目文档。

根据代码、目录结构、配置文件和已有文档，在 docs/ 目录生成（没有则创建）：

- README.md              # 项目介绍、安装、启动方式
- PROJECT_CONTEXT.md     # 项目背景、技术栈、模块说明、开发约定（最重要）
- ARCHITECTURE.md        # 项目架构、目录结构、数据流
- ROADMAP.md             # 已完成、开发中、未来规划
- CHANGELOG.md           # 当前版本及后续更新记录
- TODO.md                # 待开发功能、Bug、技术债

要求：

1. 尽量根据代码自动分析，不要凭空猜测。
2. 无法确定的信息统一标记为「待确认」。
3. 文档使用 Markdown。
4. 内容简洁、清晰、方便后续 AI 和开发者阅读。
5. 最后总结哪些内容需要我人工补充。
```

## 2.2 新对话接管项目

**Prompt**：

```text
这是一个已经开发中的项目。

请先阅读 docs 目录下的所有项目文档，包括：

- README.md
- PROJECT_CONTEXT.md
- ARCHITECTURE.md
- ROADMAP.md
- CHANGELOG.md
- TODO.md

阅读完成后：

1. 总结你对当前项目的理解。
2. 说明当前项目已经完成了什么。
3. 说明还有哪些待开发内容。
4. 如果发现文档与代码不一致，请指出并给出建议。
5. 后续所有开发都以最新代码和这些文档为准。

不要立即修改代码，等待我的下一步需求。
```

## 2.3 开发完更新

**Prompt**：

```text
本次开发已完成，请根据本次代码变更自动更新 CHANGELOG.md、PROJECT_CONTEXT.md 和 TODO.md，保持文档与代码同步。除非必要，不修改其他文档。
```

## 2.4 老项目构建

**Prompt**：

```text
请分析当前项目，并为这个已有项目补充项目文档。

请阅读：

- 项目目录结构
- 核心代码
- 配置文件
- 依赖文件
- 已有 README（如果存在）
- Git 信息（如果可以获取）

根据项目实际情况，在 docs/ 目录生成以下文件：

- README.md
  项目介绍、功能说明、安装和启动方式

- PROJECT_CONTEXT.md
  项目背景、技术栈、核心模块、开发规范，作为 AI 后续开发参考

- ARCHITECTURE.md
  项目架构、模块关系、主要流程

- ROADMAP.md
  当前完成情况、未来可能规划

- CHANGELOG.md
  根据代码和 Git 信息整理已有版本变化

- TODO.md
  当前待优化、待开发、技术债

要求：

1. 不要凭空编造，只根据代码和项目情况分析。
2. 不确定的信息标记为「待确认」。
3. 文档保持简洁、清晰，方便后续 AI Coding 使用。
4. 完成后告诉我：
   - 你对项目的整体理解
   - 哪些内容是推测
   - 哪些地方需要人工补充
```

# 第三部分：项目复盘与课堂总结

---

## 可重复的 Coding 方法（五层倒序）

1. **05 交付说明与安全收尾**——知道现在做到哪里
2. **04 联调、测试与需求验收**——亲自跑通完整路径
3. **03 分模块实现与即时验证**——一次只交付一个任务
4. **02 技术方案与任务清单**——知道为什么这样做
5. **01 需求澄清与范围边界**——先决定做什么、不做什么

## 核心方法论总结

- AI 可以快速写代码，但**你要控制方向、范围、节奏和验收**。
- 每一轮都留下明确产出，每一个小任务都立刻验证。
- 最终得到的才不是"一堆 AI 生成代码"，而是一个**你理解、敢用、能继续维护的项目**。

## 课堂主线（课程结束时你应该会自己推进项目）

- 这个案例覆盖了从模糊想法到本地可运行网页的完整 Coding 路径。
- **四轮稳定性测试负责证明需求真实存在；九环协作清单和 M1–M9 才是本课程的核心方法。**
- 课堂主线公式：`定义质量 → 制造测试 → 生成回答 → 验证稳定 → 编码工具`
- 下一项目复用指令：以 Step 05 为教学主线，复用"需求澄清 → 技术方案 → 任务拆解 → 分模块实现 → 自测 → 联调 → 验收 → 交付"的方法推进下一个 Web Coding 项目。

## 附：网页交互功能（script.js）

- **章节导航高亮**：滚动时按当前视口位置（`scrollY + 视口高度 × 32%`）判断当前章节，高亮侧边导航。
- **阅读进度条**：侧边栏竖向进度条随滚动比例增长。
- **改造前后切换**：Step 01 的"改造前 / 改造后"分段按钮切换对应面板。
- **复制按钮**：一键复制模型回答全文（`data-copy-target`）或预设指令文本（`data-copy-text`），成功/失败均有 Toast 提示（"已复制" / "复制失败，请手动选择"）。
