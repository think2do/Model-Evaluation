一句话记住

代码是工作流被理解之后的结果，不是项目的第一步。 先手工跑通流程、验证需求真实存在，再把它产品化成工具—— 这正是本项目 Step 01–04 与 Step 05 的关系。

环节00
PHASE 00 / PROJECT KICKOFF

环节 00：项目启动

主要和 AI 去聊天，将一个模糊的想法变成一个可执行的项目， 而不是直接让 AI 写代码。

METHOD / 执行清单

方法：把一个模糊想法聊成一句话定位

关键产出物

一段清晰的项目「一句话定位」+ 几点初步想法（功能方向、目标人群、大致形态）。

具体动作
  • 你：把脑子里模糊的想法用自己的话讲出来，不用讲究逻辑和完整性。
  • AI：通过提问帮你理清“这个项目到底想解决什么问题”，引导你把模糊想法聚焦成可执行的方向，而不是立刻给方案或写代码。
结束标准（DoD）
  • 你能用一两句话说出“我想做一个什么样的东西，大概解决什么问题”。
  • 想法已经从“灵感”收敛成“可以进入需求澄清阶段”的状态。
可直接发给 AI 的 PROMPT 
我有一个模糊的想法,还没想清楚细节,请不要直接给方案或写代码。
先通过提问帮我理清楚:
1. 这个想法本质上是想解决什么问题
2. 大概是给谁用的
3. 现在最核心、最想先做出来的部分是什么
一步步引导我把这个想法聊清楚,聊完之后帮我总结成一句话定位。
CASE / 本项目证据

案例补充：为什么要 Coding？

最初想法（决策日志 01）
多模型答案对比评测器——输入问题、标准与多份回答，调用 DeepSeek 评测。
  • 功能方向模型回答裁判器
  • 目标人群需要批量评测多模型回答的人
  • 大致形态可在本地运行的网页工具

把复制粘贴、逐份请求、结构校验、结果复核和排序固化成“可在本地运行的模型回答裁判器”。

想法来自已验证的手工流程：Step 01–04 手工跑通后， 重复劳动（复制粘贴、逐份请求、结果复核）成为产品化的理由—— 已验证的手工流程成为产品需求。

环节01
PHASE 01 / REQUIREMENTS

环节 01：需求澄清与范围确定

先确定“做什么”，更要确定“不做什么”； AI 把口语想法整理成结构化需求，你检查它有没有加戏。

METHOD / 执行清单

方法：把“要做什么”说清楚，并明确“不做什么”

关键产出物

一份「需求说明」文档（哪怕只有几段话）：要做什么、给谁用、核心场景是什么、明确不做什么。

具体动作
  • 你：用自己的话把想法讲清楚，哪怕模糊也先讲；明确“必须有”和“暂时不要”的功能边界。
  • AI：把你的口语化描述转成结构化需求（功能点列表 + 边界说明），并主动追问模糊点（而不是自己脑补）。
结束标准（DoD）
  • 你能一句话说清“这个项目做完是什么样子”。
  • AI 复述的需求和你脑子里想的一致，没有“AI 自己加戏”的功能。
可直接发给 AI 的 PROMPT 
请帮我把这个想法整理成结构化的需求说明,包括:
1. 核心功能点(列清单)
2. 目标用户是谁
3. 最核心的使用场景是什么
4. 明确列出"这一版先不做"的部分

将生成的文档存到项目根目录下的 `docs/*****需求文档.md`。
如果我的描述里有模糊、矛盾或者信息不够的地方,请直接指出来并追问我,
不要自己脑补细节替我做决定。
CASE / 本项目证据

案例补充：裁判器的需求说明

项目证据 《需求说明》——只做裁判器；删除出题器、后端、数据库等扩展。

需求清单是后续环节 8 验收的依据（逐条核对“完成 / 部分完成 / 不做”）。

PHASE A 需求清单（先把需求说清楚）
  • 范围只做裁判器，不做出题器
  • 输入问题、标准、回答由用户手动粘贴

  • 形态纯前端、本地使用、无数据库
  • 失败结构失败时保留原始返回，不自动修复
决策日志 03（范围纠偏）
删除“出题器”扩展——用户明确第一版只做裁判器，项目不再继续扩大。

课堂方法提示：先确定“做什么”，更要确定“不做什么”； AI 把口语想法整理成结构化需求，你检查它有没有加戏， 并确认核心用户与核心场景。

HAND-MADE PRE 1/3

手工前置 1/3：先把“什么叫做对”定义清楚

STEP 01 准备规则 在写代码前，先把“什么叫做对”定义清楚。

产出：一份边界清楚、能够被下一步直接使用的提示词模板。检查用于生成评测题的提示词，删除冲突、隐藏要求和不稳定判断。

原始目标（改写前）
“生成一道有明确区分度的模型评测题，以及与题目严格对应、可以稳定执行的二元评分标准。”
  • 对象跨领域模型能力评测
  • 交付1 道题 + 12–18 个二元评分项
  • 判定每项只允许 0 或 1 分
  • 约束不依赖隐藏信息与整体印象
关键定义（“稳定执行”）
不同裁判仅依据原始问题、评分标准和待评回答，应能按照相同证据与判定步骤得到一致结果。

原始目标正确，但部分规则之间互相拉扯，可能导致 AI 为了满足格式而硬凑内容。 改写模板把默认评分环境明确为“只看静态文本判定”。

关键改造：重复扣分规则
“每个关键缺陷只能影响最相关的一个评分项，不得重复扣分。”

问题：裁判必须判断多个失败是否来自“同一个根因”，这不是稳定的静态文本判断。

“不同评分项只要检查的是不同原子结果，就分别根据各自证据判定。”

改造：不追溯根因，只检查可观察结果；评分项设计阶段负责避免两个项目检查同一事实。

环节02
PHASE 02 / TECH DESIGN

环节 02：技术方案设计

选一个足够简单、能落地的实现方案； AI 说明取舍，你审核方案是否匹配你的能力与项目体量。

METHOD / 执行清单

方法：选择你能理解、能维护的最小方案

关键产出物
  • 技术选型说明（用什么语言 / 框架 / 库，为什么）
  • 简要架构图或文字描述（模块划分、数据怎么流转）
  • 如果涉及数据存储：数据结构 / 表结构草图
具体动作
  • AI：给出可行技术方案，说明取舍（不是直接甩一堆代码）。
  • 你：审核方案是否匹配你的能力（能不能维护）、是否匹配项目体量（别小项目上重架构）。
结束标准（DoD）
  • 你能看懂并解释“为什么选这个方案”，而不是“AI 说了算，我不懂”。
  • 方案里没有你完全陌生、且 AI 也没解释清楚的黑盒技术。
如果 AI 给的方案你看不懂，怎么办

不要假装懂了直接往下走——这是后面失控的最大源头之一

  1. 直接跟 AI 说：“用大白话 / 打比方跟我解释一遍，不要用专业术语。”
  2. “假设我是完全不懂技术的人，你要怎么跟我讲清楚这个方案在做什么。”
  3. “有没有更简单、但够用的方案？哪怕性能 / 扩展性差一点也没关系。”
  4. “这个技术我以后自己改代码的时候，最容易在哪里踩坑？”

判断标准：如果 AI 解释完，你还是没法用自己的话复述一遍“这个方案大概是怎么回事”， 说明还没讲清楚，继续追问，别往下走。遇到绕不开的专业名词， 让 AI 用你熟悉的东西打比方（生活场景、你已经会的其他工具）， 而不是用另一个你也不懂的术语解释一个术语。

可直接发给 AI 的 PROMPT 
基于以上确定的需求,请给我可行的技术方案。

对每个方案请说明:
1. 技术选型说明(用什么语言/框架/库,为什么)
2. 简要架构图或文字描述(模块划分、数据怎么流转)
3. 如果涉及数据存储:数据结构/表结构草图
4. 大致用什么技术/工具(不用列太细)
5. 优缺点和取舍是什么
6. 用大白话/打比方讲清楚这个方案是在做什么,不要堆专业术语

将生成的文档存到项目根目录下的 `docs/*****技术方案.md`。
最后请告诉我这个方案里有没有"我以后自己改代码时特别容易踩坑"的地方。

环节03
PHASE 03 / TASK BREAKDOWN

环节 03：任务拆解与排期

把大需求拆成可验证的小任务； 每个任务都能在一次对话、一个 commit 内完成并单独验收。

METHOD / 执行清单

方法：拆成一次对话能验收的小任务

关键产出物

一份任务清单（Task List）：按模块 / 功能拆成可独立验收的小任务，每个任务能在一次对话 / 一个 commit 内完成。

具体动作
  • AI：把大需求拆成小任务，标注任务间的依赖关系（哪个必须先做）。
  • 你：检查拆分粒度是否合理——太大你就没法中途检查，太碎会失去整体感。
结束标准（DoD）
  • 每个任务都有清晰的“验收方式”（比如“这个函数输入 A 输出 B”“这个页面能看到 X”）。
  • 你知道接下来要按什么顺序推进，不是走一步看一步。
可直接发给 AI 的 PROMPT 
请把我们确定的方案拆解成一个具体的任务清单。

要求:
1. 每个任务要足够小,能在一次对话/一次提交里做完
2. 标注任务之间的先后依赖关系(哪个必须先做完才能做下一个)
3. 每个任务都附上"怎么算这个任务做完了"的验收标准
   (要具体到我能亲自操作验证,比如"打开某页面应该看到什么"
   或"调用某个函数输入什么应该输出什么")

将生成的文档存到项目根目录下的 `docs/*****任务清单.md`。
请按顺序编号列出。

AI 天然倾向于一口气多做，你需要主动“喊停”、分批验证。 之前项目不理想，大概率就出在环节 5–6：AI 一次产出太多， 你没能逐块验证，问题堆积到后面才爆发。 上一块没有看懂、没有验证，就不进入下一块。

本项目证据 网页 Step 05 的推进方式（“开始 M2 / M3 / … / M9”）本质上是在控制风险。

课堂观察（人机分工）：这次 Vibe Coding 的核心不是“AI 写了多少代码”，而是人持续负责方向、取舍和验收，AI 负责结构化、实现、解释和暴露风险。

PART Ⅱ / MAINTENANCE

第二部分：
维护项目（文档与交接）

项目开发完成后，如何让文档与代码保持同步、 如何让新对话 / 老项目顺利接管。

2.1

初始化项目文档

让 AI 完整阅读当前项目，在 docs/ 目录生成六份文档：README、PROJECT_CONTEXT、ARCHITECTURE、ROADMAP、CHANGELOG、TODO。要求根据代码自动分析，无法确定的信息标记「待确认」。

可发给 AI 的 PROMPT 
请先完整阅读当前项目，然后自动整理项目文档。

根据代码、目录结构、配置文件和已有文档，在 docs/ 目录生成（没有则创建）：

- README.md              # 项目介绍、安装、启动方式
- PROJECT_CONTEXT.md     # 项目背景、技术栈、模块说明、开发约定（最重要）
- ARCHITECTURE.md        # 项目架构、目录结构、数据流
- ROADMAP.md             # 已完成、开发中、未来规划
- CHANGELOG.md           # 当前版本及后续更新记录
- TODO.md                # 待开发功能、Bug、技术债

要求：

1. 尽量根据代码自动分析，不要凭空猜测。
2. 无法确定的信息统一标记为「待确认」。
3. 文档使用 Markdown。
4. 内容简洁、清晰、方便后续 AI 和开发者阅读。
5. 最后总结哪些内容需要我人工补充。
2.2

新对话接管项目

新对话开始前，先读 docs/ 下全部文档，总结理解、说明完成度与待开发内容，发现文档与代码不一致时指出；不要立即修改代码，等待下一步需求。

可发给 AI 的 PROMPT 
这是一个已经开发中的项目。

请先阅读 docs 目录下的所有项目文档，包括：

- README.md
- PROJECT_CONTEXT.md
- ARCHITECTURE.md
- ROADMAP.md
- CHANGELOG.md
- TODO.md

阅读完成后：

1. 总结你对当前项目的理解。
2. 说明当前项目已经完成了什么。
3. 说明还有哪些待开发内容。
4. 如果发现文档与代码不一致，请指出并给出建议。
5. 后续所有开发都以最新代码和这些文档为准。

不要立即修改代码，等待我的下一步需求。
2.3

开发完更新

每次开发完成后，让 AI 根据本次代码变更自动更新 CHANGELOG、PROJECT_CONTEXT 和 TODO，保持文档与代码同步；除非必要，不修改其他文档。

可发给 AI 的 PROMPT 
本次开发已完成，请根据本次代码变更自动更新 CHANGELOG.md、PROJECT_CONTEXT.md 和 TODO.md，保持文档与代码同步。除非必要，不修改其他文档。
2.4

老项目构建

面对没有文档的已有项目，让 AI 分析目录结构、核心代码、配置、依赖、README 与 Git 信息，按实际生成 docs/ 六份文档，不凭空编造。

可发给 AI 的 PROMPT 
请分析当前项目，并为这个已有项目补充项目文档。

请阅读：

- 项目目录结构
- 核心代码
- 配置文件
- 依赖文件
- 已有 README（如果存在）
- Git 信息（如果可以获取）

根据项目实际情况，在 docs/ 目录生成以下文件：

- README.md
  项目介绍、功能说明、安装和启动方式

- PROJECT_CONTEXT.md
  项目背景、技术栈、核心模块、开发规范，作为 AI 后续开发参考

- ARCHITECTURE.md
  项目架构、模块关系、主要流程

- ROADMAP.md
  当前完成情况、未来可能规划

- CHANGELOG.md
  根据代码和 Git 信息整理已有版本变化

- TODO.md
  当前待优化、待开发、技术债

要求：

1. 不要凭空编造，只根据代码和项目情况分析。
2. 不确定的信息标记为「待确认」。
3. 文档保持简洁、清晰，方便后续 AI Coding 使用。
4. 完成后告诉我：
   - 你对项目的整体理解
   - 哪些内容是推测
   - 哪些地方需要人工补充
