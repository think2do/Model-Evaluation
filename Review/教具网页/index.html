一句话记住

代码是工作流被理解之后的结果，不是项目的第一步。 先手工跑通流程、验证需求真实存在，再把它产品化成工具。

🎤 演讲者注释

给听众一张全局地图。第一部分是“从 0 到 1 怎么做”，第二部分是“做完之后文档怎么跟上、项目怎么交接”， 第三部分是“离开课堂时带走什么”。三部分各自独立成块，中间穿插案例证据页。

第一部分：
十个环节总览

这是“执行清单”而非“流程参观”——每一步都有明确的产出物、人机分工和结束标准（DoD）。

环节00
PHASE 00 / PROJECT KICKOFF

环节 0：项目启动

跟 AI 聊天把模糊想法收敛成可执行方向，而不是直接让 AI 写代码。

关键产出物

一句话定位 + 初步想法（功能方向、目标人群、大致形态）。

具体动作
  • 你：用自己的话讲出模糊想法（不用讲究逻辑）。
  • AI：通过提问帮你理清“到底想解决什么问题”。
结束标准（DoD）
  • 能用一两句话说出“想做什么、大概解决什么问题”。
  • 从“灵感”收敛到“可以进需求澄清”。
案例证据 代码是工作流被理解之后的结果，不是项目的第一步。

想法来自已验证的手工流程（Step 01–04）——重复劳动（复制粘贴、逐份请求、结果复核）成为产品化理由。一句话记住：已验证的手工流程成为产品需求。

🎤 演讲者注释

讲解方法时带出 Prompt 要点——“不要给方案、先通过提问帮我理清楚”。 本项目证据非常关键：最初不是“想写个网页”，而是先有了一套手工评测流程， 因为重复劳动太多，才产生“做成工具”的需求。可以反问听众：“你手上有没有重复劳动，值得做成工具？”

环节 0 · 项目启动

可直接发给 AI 的 Prompt

📋 PROMPT 00 
我有一个模糊的想法,还没想清楚细节,请不要直接给方案或写代码。
先通过提问帮我理清楚:
1. 这个想法本质上是想解决什么问题
2. 大概是给谁用的
3. 现在最核心、最想先做出来的部分是什么
一步步引导我把这个想法聊清楚,聊完之后帮我总结成一句话定位。

要点：不要给方案、先通过提问帮我理清楚，最后落成一句话定位。

环节01
PHASE 01 / REQUIREMENTS

环节 1：需求澄清与范围确定

先确定“做什么”，更要确定“不做什么”；AI 不自己脑补，你检查它有没有“加戏”。

关键产出物

《需求说明》——要做什么、给谁用、核心场景、明确不做什么。

具体动作
  • 你：讲清想法 + 划清“必须有 / 暂时不要”的边界。
  • AI：口语描述 → 结构化需求，主动追问模糊点，不自己脑补。
结束标准（DoD）
  • 一句话说清“做完是什么样子”。
  • AI 复述的需求和你脑子里想的一致，没有“AI 自己加戏”的功能。
案例证据 · PHASE A 需求清单
  • 范围只做裁判器，不做出题器
  • 形态纯前端、本地使用、无数据库
  • 失败结构失败保留原始返回，不自动修复
决策日志 03（范围纠偏）
删除“出题器”扩展——先确定做什么，更要确定不做什么。

关键：需求清单是环节 8 验收的依据（逐条核对 完成 / 部分完成 / 不做）。

🎤 演讲者注释

重点讲“AI 加戏”这个概念——AI 整理需求后，你要逐条检查它有没有擅自加功能、替你拍板。 本项目三次范围纠偏：只做裁判器、删出题器、删后端数据库。范围控制不是“少做”，而是“这一版做完、做扎实”。

环节 1 · 需求澄清

可直接发给 AI 的 Prompt

📋 PROMPT 01 
请帮我把这个想法整理成结构化的需求说明,包括:
1. 核心功能点(列清单)
2. 目标用户是谁
3. 最核心的使用场景是什么
4. 明确列出"这一版先不做"的部分

将生成的文档存到项目根目录下的 `docs/*****需求文档.md`。
如果我的描述里有模糊、矛盾或者信息不够的地方,请直接指出来并追问我,
不要自己脑补细节替我做决定。

要点：让 AI 主动追问模糊点，不要自己脑补；文档存到 docs/。

案例1
CASE 01 / 写代码前的准备

环节 1 案例：三个手工前置

需求澄清不止是写文档，还要制造出“可评测的材料”。

1/3 STEP 01 准备规则 定义“什么叫做对”——删除冲突、隐藏要求和不稳定判断；“稳定执行”= 不同裁判凭相同证据得到一致结果。
2/3 STEP 02 准备测试 抽象目标 → 可观察要求：“有网感”不直接评价，而是要求首句有钩子、固定对比句式、回复指定关键词、emoji ≤ 3；产出题目 + 13 项评分标准（C01–C13）。
3/3 STEP 03 准备回答 题目 → 模型生成回答 → 可被重复裁判的静态材料；网页评测的是“用户粘贴进来的回答”，不是自动生成答案。
改造前后（STEP 01）：重复扣分规则
“每个关键缺陷只能影响最相关的一个评分项，不得重复扣分。”

问题：裁判必须判断多个失败是否来自“同一个根因”，这不是稳定的静态文本判断。

“不同评分项只要检查的是不同原子结果，就分别根据各自证据判定。”

改造：不追溯根因，只检查可观察结果；评分项设计阶段避免两个项目检查同一事实。

课堂观察

13 项评分标准是全场最重要的基准物：环节 6 的稳定性测试、环节 8 的验收都以它为准。

环节02
PHASE 02 / TECH DESIGN

环节 2：技术方案设计

AI 给出可行方案并说明取舍；你审核方案是否匹配你的能力与项目体量。

关键产出物
  • 技术选型说明（语言 / 框架 / 库、为什么）
  • 简要架构或数据流转
  • 数据结构草图（如需）
具体动作
  • AI：给出可行方案并说明取舍（不是直接甩代码）。
  • 你：审核方案是否匹配你的能力（能维护）、匹配项目体量（别小项目上重架构）。
结束标准（DoD）
  • AI 讲完后，你能用自己的话复述“这个方案大概怎么回事”，才往下走。
  • 方案里没有你完全陌生、且 AI 也没解释清楚的黑盒技术。
看不懂方案怎么办

不要假装懂了往下走——这是后面失控的最大源头之一

  1. “用大白话 / 打比方跟我解释一遍。”
  2. “假设我是完全不懂技术的人，怎么讲清楚这个方案在做什么。”
  3. “有没有更简单但够用的方案？性能差一点没关系。”
🎤 演讲者注释

强调“看不懂就问到底”是这一环节最重要的动作——“假装懂了”是后面失控的最大源头之一。 本项目为什么选纯静态三件套？因为匹配体量：本地单人使用的裁判器，不需要框架、构建和数据库。

环节 2 · 技术方案

可直接发给 AI 的 Prompt

📋 PROMPT 02 
基于以上确定的需求,请给我可行的技术方案。

对每个方案请说明:
1. 技术选型说明(用什么语言/框架/库,为什么)
2. 简要架构图或文字描述(模块划分、数据怎么流转)
3. 如果涉及数据存储:数据结构/表结构草图
4. 大致用什么技术/工具(不用列太细)
5. 优缺点和取舍是什么
6. 用大白话/打比方讲清楚这个方案是在做什么,不要堆专业术语

将生成的文档存到项目根目录下的 `docs/*****技术方案.md`。
最后请告诉我这个方案里有没有"我以后自己改代码时特别容易踩坑"的地方。

要点：要取舍、要大白话打比方；并提示“以后改代码容易踩坑的地方”。

环节03
PHASE 03 / TASK BREAKDOWN

环节 3：任务拆解与排期

把大需求拆成可独立验收的小任务——每个任务能在一次对话 / 一个 commit 内完成。

关键产出物

任务清单（Task List）——每个任务可在一次对话 / 一个 commit 内完成，可独立验收。

具体动作
  • AI：把大需求拆成小任务，标注任务间依赖（哪个必须先做）。
  • 你：检查拆分粒度——太大没法中途检查，太碎失去整体感。
结束标准（DoD）
  • 每个任务有清晰验收方式（“输入 A 输出 B”“页面能看到 X”）。
  • 知道推进顺序，不是走一步看一步。
01需求说明做什么 / 给谁 / 核心场景 / 不做什么
→
02技术与架构纯前端三件套与数据流
→
03任务清单拆成 9 个单次可验收任务
Git 边界（诚实原则） M3 → M4 → M5 → M6 → M7 → M7.1 → M8 → M9

当前仓库可见记录从 M3 开始，就不能把 M1、M2 说成独立提交。这既是方法也是态度。

🎤 演讲者注释

本页强调两件事：一是验收标准必须具体到能亲自操作验证； 二是诚实对待 Git 历史——可见记录从 M3 开始，就不能把 M1、M2 说成独立提交。

环节 3 · 任务拆解

可直接发给 AI 的 Prompt

📋 PROMPT 03 
请把我们确定的方案拆解成一个具体的任务清单。

要求:
1. 每个任务要足够小,能在一次对话/一次提交里做完
2. 标注任务之间的先后依赖关系(哪个必须先做完才能做下一个)
3. 每个任务都附上"怎么算这个任务做完了"的验收标准
   (要具体到我能亲自操作验证,比如"打开某页面应该看到什么"
   或"调用某个函数输入什么应该输出什么")

将生成的文档存到项目根目录下的 `docs/*****任务清单.md`。
请按顺序编号列出。

要点：任务小到一次对话/一次提交可完成，附“能亲自操作验证”的验收标准。

环节04
PHASE 04 / SCAFFOLDING

环节 4：环境搭建与脚手架

“跑起来”必须由你亲自完成——AI 说能跑不算数。

关键产出物
  • 可运行的项目骨架（能启动、能看到空白页面 / 接口返回 200）
  • 目录结构说明
具体动作
  • AI：搭建项目结构、配置基础依赖。
  • 你：亲自跑一遍启动命令，确认在自己机器上真的能跑。
结束标准（DoD）
  • 本地成功启动无报错。
  • 理解目录结构里“哪个文件夹放什么”的基本逻辑。
案例证据 · M1 基础页面 index.html + styles.css + app.js，纯静态可直接打开，无需构建。

骨架内容：输入区 / 结果区 / 空状态——空状态是页面“名词”与区域的第一版雏形。

🎤 演讲者注释

强调“跑起来”这件事必须由你亲自完成——AI 说能跑不算数。本项目打开方式最简单： 直接双击 index.html，或起任意静态文件服务器。骨架阶段的“空状态”很有价值， 它提前定义了页面有哪些区域，后面每个模块都往这些区域里填内容。

环节 4 · 环境搭建

可直接发给 AI 的 Prompt

📋 PROMPT 04 
请帮我搭建这个项目的基础脚手架(目录结构 + 必要依赖),先不用写业务逻辑。

完成后请告诉我:
1. 目录结构里每个主要文件夹/文件是干嘛的(简单一句话说明)
2. 我需要在终端里依次敲哪些命令,才能把项目跑起来
3. 跑起来之后,我应该在浏览器/终端里看到什么,
   才能确认"搭建成功了"

要点：让 AI 告诉你怎么启动、启动后应看到什么，然后亲自跑一遍。

环节05
PHASE 05 / MODULAR BUILD

环节 5：分模块开发实现

每次只做一个约定好的小任务，做完立刻验证——不要攒到最后一起看。

关键产出物

按环节 3 任务清单逐个交付的功能代码（每次一个小任务，不一次甩一大坨）。

具体动作
  • AI：每次只做一个约定好的小任务，做完主动说明“改了什么文件、实现了什么逻辑”。
  • 你：每个小任务做完后立刻验证——这是最容易失控的环节。
结束标准（DoD）
  • 当前任务功能你亲自验证过（跑起来、点按钮、发请求）。
  • 没有“AI 说做完了，但我没看”的任务。
案例证据 M2 → M8 逐项推进——输入、回答、请求、解析、展示、排序分别交付。

每轮要求说明改了什么、怎样验收，再决定下一项。

🎤 演讲者注释

这页是“节奏控制”的核心。AI 天然倾向于一口气多做，你要主动喊停、分批验证。 可执行习惯：每个任务完成后让 AI 回答三个问题——①改了哪些文件 ②每处改动实现了什么逻辑（大白话） ③我怎么操作才能验证成功。验证通过才 commit。

环节 5 · 分模块开发

可直接发给 AI 的 Prompt

📋 PROMPT 05 
现在请只完成任务清单里的【任务X:具体任务名】,不要顺带做其他任务。
每次执行一个任务并进行验证,待验证通过后提交一个commit后再开始下一个任务,
不要一次性做完所有任务再验证。

每一步做完之后请告诉我:
1. 改动了哪些文件(简单列出,不用贴全部代码)
2. 每处改动实现了什么逻辑(用大白话说)
3. 需要我验证的告诉我应该怎么操作才能验证这个任务确实做成了
   (具体到"打开哪个页面/敲哪条命令/点哪个按钮,应该看到什么结果")

要点：一次只做一个任务；验证通过才 commit，再进下一个。

PART Ⅲ / REVIEW 2/3

核心方法论 + 课堂主线

核心方法论
AI 可以快速写代码，但你要控制方向、范围、节奏和验收。

每一轮都留下明确产出，每一个小任务都立刻验证——最终得到的是你理解、敢用、能继续维护的项目。

课堂主线
四轮稳定性测试证明需求真实存在；九环协作清单和 M1–M9 才是本课程的核心方法。

课堂主线公式：定义质量 → 制造测试 → 生成回答 → 验证稳定 → 编码工具。

下一项目复用指令 需求澄清 → 技术方案 → 任务拆解 → 分模块实现 → 自测 → 联调 → 验收 → 交付
🎤 演讲者注释

把“会聊天”升级成“会 Coding”的关键：人在回路（Human-in-the-loop）——AI 提供速度，人提供方向。 课堂主线公式对应到手工前置：定义质量（STEP 01）→ 制造测试（STEP 02）→ 生成回答（STEP 03）→ 验证稳定（STEP 04）→ 编码工具（Step 05）。
