# Web Coding × AI 协作执行清单(需求 → 开发完成)

# 一、构建项目

> 范围:从需求澄清开始,到代码开发完成为止,不含部署运维。
> 定位:每个环节回答四个问题——**产出物是什么 / AI做什么 / 你做什么 / 什么算完成**。

---
## 环节 0:项目启动

主要和AI去聊天将一个模糊的想法变成一个可执行的项目,而不是直接让AI写代码。

**关键产出物**
- 一段清晰的项目「一句话定位」+ 几点初步想法(功能方向、目标人群、大致形态)

**具体动作**
- 你:把脑子里模糊的想法用自己的话讲出来,不用讲究逻辑和完整性
- AI:通过提问帮你理清"这个项目到底想解决什么问题",引导你把模糊想法聚焦成可执行的方向,而不是立刻给方案或写代码

**结束标准(DoD)**
- 你能用一两句话说出"我想做一个什么样的东西,大概解决什么问题"
- 想法已经从"灵感"收敛成"可以进入需求澄清阶段"的状态

**可直接发给 AI 的 Prompt**
```
我有一个模糊的想法,还没想清楚细节,请不要直接给方案或写代码。
先通过提问帮我理清楚:
1. 这个想法本质上是想解决什么问题
2. 大概是给谁用的
3. 现在最核心、最想先做出来的部分是什么
一步步引导我把这个想法聊清楚,聊完之后帮我总结成一句话定位。
```

## 环节 1:需求澄清与范围确定

**关键产出物**
- 一份「需求说明」文档(哪怕只有几段话):要做什么、给谁用、核心场景是什么、明确不做什么

**具体动作**
- 你:用自己的话把想法讲清楚,哪怕模糊也先讲;明确"必须有"和"暂时不要"的功能边界
- AI:把你的口语化描述转成结构化需求(功能点列表 + 边界说明),并主动追问模糊点(而不是自己脑补)

**结束标准(DoD)**
- 你能一句话说清"这个项目做完是什么样子"
- AI 复述的需求和你脑子里想的一致,没有"AI 自己加戏"的功能

**可直接发给 AI 的 Prompt**
```
请帮我把这个想法整理成结构化的需求说明,包括:
1. 核心功能点(列清单)
2. 目标用户是谁
3. 最核心的使用场景是什么
4. 明确列出"这一版先不做"的部分

将生成的文档存到项目根目录下的 `docs/*****需求文档.md`。
如果我的描述里有模糊、矛盾或者信息不够的地方,请直接指出来并追问我,
不要自己脑补细节替我做决定。
```

## 环节 2:技术方案设计

**关键产出物**
- 技术选型说明(用什么语言/框架/库,为什么)
- 简要架构图或文字描述(模块划分、数据怎么流转)
- 如果涉及数据存储:数据结构/表结构草图

**具体动作**
- AI:给出个可行技术方案,说明取舍(不是直接甩一堆代码)
- 你:审核方案是否匹配你的能力(能不能维护)、是否匹配项目体量(别小项目上重架构)

**如果 AI 给的方案你看不懂,怎么办**
- 不要假装懂了直接往下走,这是后面失控的最大源头之一。可以直接这样跟 AI 说:
  - "用大白话/打比方跟我解释一遍,不要用专业术语"
  - "假设我是完全不懂技术的人,你要怎么跟我讲清楚这个方案在做什么"
  - "有没有更简单、但够用的方案?哪怕性能/扩展性差一点也没关系"
  - "这个技术我以后自己改代码的时候,最容易在哪里踩坑?"
- 判断标准很简单:如果 AI 解释完,你还是没法用自己的话复述一遍"这个方案大概是怎么回事",说明还没讲清楚,继续追问,别往下走。
- 遇到实在绕不开的专业名词(比如某个框架、某种架构模式),可以让 AI 用你熟悉的东西打比方(生活场景、你已经会的其他工具),而不是用另一个你也不懂的术语解释一个术语。

**结束标准(DoD)**
- 你能看懂并解释"为什么选这个方案",而不是"AI说了算,我不懂"
- 方案里没有你完全陌生、且 AI 也没解释清楚的黑盒技术

**可直接发给 AI 的 Prompt**
```
基于以上确定的需求,请给我可行的技术方案。

对每个方案请说明:
1. 技术选型说明(用什么语言/框架/库,为什么)
2. 简要架构图或文字描述(模块划分、数据怎么流转)
3. 如果涉及数据存储:数据结构/表结构草图
4. 大致用什么技术/工具(不用列太细)
5. 优缺点和取舍是什么
6. 用大白话/打比方讲清楚这个方案是在做什么,不要堆专业术语

将生成的文档存到项目根目录下的 `docs/*****技术方案.md`。
最后请告诉我这个方案里有没有"我以后自己改代码时特别容易踩坑"的地方。
```

## 环节 3:任务拆解与排期

**关键产出物**
- 一份任务清单(Task List):按模块/功能拆成可独立验收的小任务,每个任务能在一次对话/一个commit内完成

**具体动作**
- AI:把大需求拆成小任务,标注任务间的依赖关系(哪个必须先做)
- 你:检查拆分粒度是否合理——太大你就没法中途检查,太碎会失去整体感

**结束标准(DoD)**
- 每个任务都有清晰的"验收方式"(比如"这个函数输入A输出B""这个页面能看到X")
- 你知道接下来要按什么顺序推进,不是走一步看一步

**可直接发给 AI 的 Prompt**
```
请把我们确定的方案拆解成一个具体的任务清单。

要求:
1. 每个任务要足够小,能在一次对话/一次提交里做完
2. 标注任务之间的先后依赖关系(哪个必须先做完才能做下一个)
3. 每个任务都附上"怎么算这个任务做完了"的验收标准
   (要具体到我能亲自操作验证,比如"打开某页面应该看到什么"
   或"调用某个函数输入什么应该输出什么")

将生成的文档存到项目根目录下的 `docs/*****任务清单.md`。
请按顺序编号列出。
```

## 环节 4:环境搭建与脚手架

**关键产出物**
- 可运行的项目骨架(能启动、能看到空白页面/接口返回200)
- 目录结构说明

**具体动作**
- AI:搭建项目结构,配置好基础依赖
- 你:亲自跑一遍启动命令,确认在你自己的机器上真的能跑起来(不是只在AI的描述里能跑)

**结束标准(DoD)**
- 项目在你本地成功启动,没有报错
- 你理解目录结构里"哪个文件夹放什么"的基本逻辑

**可直接发给 AI 的 Prompt**
```
请帮我搭建这个项目的基础脚手架(目录结构 + 必要依赖),先不用写业务逻辑。

完成后请告诉我:
1. 目录结构里每个主要文件夹/文件是干嘛的(简单一句话说明)
2. 我需要在终端里依次敲哪些命令,才能把项目跑起来
3. 跑起来之后,我应该在浏览器/终端里看到什么,
   才能确认"搭建成功了"
```

## 环节 5:分模块开发实现

**关键产出物**
- 按环节3的任务清单,逐个交付的功能代码(每次一个小任务,而不是一次性甩一大坨)

**具体动作**
- AI:每次只做一个约定好的小任务,做完主动说明"改了什么文件、实现了什么逻辑"
- 你:**每个小任务做完后立刻验证**,不要攒到最后一起看(这是最容易失控的环节)

**结束标准(DoD)**
- 当前任务对应的功能,你亲自验证过(跑起来看、点一下按钮、发个请求),确实符合预期
- 没有"AI说做完了,但我没看"的任务

**可直接发给 AI 的 Prompt**
```
现在请只完成任务清单里的【任务X:具体任务名】,不要顺带做其他任务。
每次执行一个任务并进行验证，待验证通过后提交一个commit后再开始下一个任务，不要一次性做完所有任务再验证。

每一步做完之后请告诉我:
1. 改动了哪些文件(简单列出,不用贴全部代码)
2. 每处改动实现了什么逻辑(用大白话说)
3. 需要我验证的告诉我应该怎么操作才能验证这个任务确实做成了
   (具体到"打开哪个页面/敲哪条命令/点哪个按钮,应该看到什么结果")
```

## 环节 6:自测与代码走查

**关键产出物**
- 关键逻辑的测试结果(哪怕是手动测试记录,不一定要写自动化测试)
- 一份"已知问题/边界情况"清单

**具体动作**
- AI:主动列出这段代码没覆盖到的边界情况、可能的bug点
- 你:挑几个边界场景(比如空输入、异常输入)亲自试一下,不要只测"正常路径"

**结束标准(DoD)**
- 正常场景和至少1-2个异常场景都手动验证过
- 已知的坑(哪怕暂时不修)你是清楚的,而不是"看起来能用就行"

**可直接发给 AI 的 Prompt**
```
请针对刚才实现的【具体功能/模块名】,帮我做一次自查:

1. 列出这段代码可能没覆盖到的边界情况和潜在 bug 点
   (比如空输入、异常输入、极端值、网络失败等)
2. 针对每一条,给我具体的手动测试步骤,让我可以逐一验证
   (不需要写自动化测试代码,手动操作步骤就行)
3. 哪些问题你觉得现在必须修,哪些可以先记下来暂不处理
```

## 环节 7:集成联调

**关键产出物**
- 各模块拼在一起后,端到端能跑通的一个完整流程(比如"从首页点击到提交成功"全流程)

**具体动作**
- AI:把之前分开开发的模块接起来,解决接口/数据格式不匹配的问题
- 你:走一遍完整用户路径,而不是只看单个模块

**结束标准(DoD)**
- 核心使用路径(你在环节1定义的核心场景)能从头到尾走通一次
- 没有"模块A单独能跑,模块B单独能跑,但连起来就报错"的情况

**可直接发给 AI 的 Prompt**
```
现在请帮我把已经完成的各个模块整合起来,
确保【核心使用路径,比如"从首页到提交成功"】能完整走通。

整合完成后请给我一份端到端的操作步骤清单,
让我能从头到尾亲自走一遍这个流程来验证。

如果整合过程中发现模块之间接口/数据格式对不上,
请说明是怎么解决的。
```

## 环节 8:测试与验收

**关键产出物**
- 对照环节1的需求清单,逐条打勾的验收结果
- 遗留问题清单(哪些是这一版不修的,明确记下来而不是遗忘)

**具体动作**
- 你:拿着最初的需求清单,一条条核对是否做到
- AI:协助定位任何"做出来但不符合预期"的问题根因

**结束标准(DoD)**
- 需求清单里的每一条,状态是"完成/部分完成/不做",而不是"不确定"
- 你敢把这个版本给别人用,而不是心里没底

**可直接发给 AI 的 Prompt**
```
这是我们最初环节1确定的需求清单:
[把环节1的需求清单粘贴到这里]

请逐条核对当前代码是否满足,并标注每一条的状态:
完成 / 部分完成 / 未做

对于"部分完成"或"未做"的条目,请说明原因,
以及不做/没做完会有什么实际影响。
```

---

## 环节 9:开发完成确认(交付前收尾)

**关键产出物**
- 最终代码 + 一份简要说明(怎么运行、有什么已知限制)

**具体动作**
- AI:整理一份"这个版本做了什么、没做什么、怎么跑"的总结
- 你:通读一遍,确认这份总结和你的理解一致

**结束标准(DoD)**
- 即使过一个月你回来看这份说明,也能知道当时做到了哪一步
- 项目状态是"我清楚现在的样子",而不是"AI说做完了我就信了"

**可直接发给 AI 的 Prompt**
```
请帮我整理一份这个版本的总结文档,包括:

1. 这个版本做了哪些功能(简明列出)
2. 有哪些已知限制或还没做完的部分
3. 怎么运行这个项目(命令 + 步骤)
4. 如果我以后要接着改这个项目,有什么需要特别注意的地方
   (比如容易踩坑的模块、临时方案以后要替换的地方等)
```

## 贯穿全流程的一条原则

**AI 交付节奏 vs 你的验证节奏要匹配**——AI 天然倾向于一口气多做,你需要主动"喊停"、分批验证。之前项目不理想,大概率就出在环节5-6:AI一次产出太多,你没能逐块验证,问题堆积到后面才爆发。

*后续如果需要,可以针对某一个环节(比如"环节5:分模块开发实现"或"环节6:自测与代码走查")进一步拆细到具体的对话话术和检查清单。*


# 二、维护项目
## 2.1 初始化项目文档

```
请先完整阅读当前项目，然后自动整理项目文档。

根据代码、目录结构、配置文件和已有文档，在 docs/ 目录生成（没有则创建）：

- README.md              # 项目介绍、安装、启动方式
- PROJECT_CONTEXT.md     # 项目背景、技术栈、模块说明、开发约定（最重要）
- ARCHITECTURE.md        # 项目架构、目录结构、数据流
- ROADMAP.md             # 已完成、开发中、未来规划
- CHANGELOG.md           # 当前版本及后续更新记录
- TODO.md                # 待开发功能、Bug、技术债

要求：

1. 尽量根据代码自动分析，不要凭空猜测。
2. 无法确定的信息统一标记为「待确认」。
3. 文档使用 Markdown。
4. 内容简洁、清晰、方便后续 AI 和开发者阅读。
5. 最后总结哪些内容需要我人工补充。
```


## 2.2 新对话接管项目
```
这是一个已经开发中的项目。

请先阅读 docs 目录下的所有项目文档，包括：

- README.md
- PROJECT_CONTEXT.md
- ARCHITECTURE.md
- ROADMAP.md
- CHANGELOG.md
- TODO.md

阅读完成后：

1. 总结你对当前项目的理解。
2. 说明当前项目已经完成了什么。
3. 说明还有哪些待开发内容。
4. 如果发现文档与代码不一致，请指出并给出建议。
5. 后续所有开发都以最新代码和这些文档为准。

不要立即修改代码，等待我的下一步需求。
```


## 2.3 开发完更新
```
本次开发已完成，请根据本次代码变更自动更新 CHANGELOG.md、PROJECT_CONTEXT.md 和 TODO.md，保持文档与代码同步。除非必要，不修改其他文档。
```

## 2.4 老项目构建
```
请分析当前项目，并为这个已有项目补充项目文档。

请阅读：

- 项目目录结构
- 核心代码
- 配置文件
- 依赖文件
- 已有 README（如果存在）
- Git 信息（如果可以获取）

根据项目实际情况，在 docs/ 目录生成以下文件：

- README.md
  项目介绍、功能说明、安装和启动方式

- PROJECT_CONTEXT.md
  项目背景、技术栈、核心模块、开发规范，作为 AI 后续开发参考

- ARCHITECTURE.md
  项目架构、模块关系、主要流程

- ROADMAP.md
  当前完成情况、未来可能规划

- CHANGELOG.md
  根据代码和 Git 信息整理已有版本变化

- TODO.md
  当前待优化、待开发、技术债

要求：

1. 不要凭空编造，只根据代码和项目情况分析。
2. 不确定的信息标记为「待确认」。
3. 文档保持简洁、清晰，方便后续 AI Coding 使用。
4. 完成后告诉我：
   - 你对项目的整体理解
   - 哪些内容是推测
   - 哪些地方需要人工补充
```
